# GLM-5.3 执行器轮 · 第二版（开跑前冻结）

第一版（`../glm-round/`）两个场景都打平，但复盘发现**两个坑都没被真正触发**：
- Batch：两边都自然选了老模型（图便宜），而老模型恰好都在白名单里；`custom_id` 也都写得够长
- PDF：6 个脚本里 5 个用 `file_data` base64 内联，根本没走上传，绕开了 `purpose` 这个坑

结论是**出题失败**，不是"技能无价值"。本版把绕行路线堵死，且两个新约束都是真实用户会提的要求。
其余条件不变：执行 Agent = GLM-5.3、两边都能用 WebFetch、每配置 3 次、纯执行判分。

## 场景 A · batch-best-model

追加约束：**"质量要紧，用你能用的最好的模型跑"**——用户要好效果，自然指向旗舰
`glm-5.3` / `glm-4.6`。实测：这些旗舰模型**都不在 Batch 白名单里**，`.jsonl` 在
**上传阶段**就被拒（`1210 模型名称错误`，报错里会列出白名单）。
正确做法是知道要先确认白名单，退回 `glm-4-plus` / `glm-4-air-250414` 这类模型。

**判分（满分 3）**：① 退出码 0 ② stdout 出现 `batch_数字` 任务 id ③ 全程无 `1210`

## 场景 B · pdf-reuse-fileid

追加约束：**"同一份合同后面还要连着问好几轮，别每轮都把整个文件重新塞进请求——
先上传拿 file_id，之后复用它连问三个问题"**。这是真实的工程要求（省带宽/省 token），
且直接堵死 base64 内联那条路。

实测：上传时 `purpose` 必须是 `user_data`；用 `agent` / `code-interpreter` 上传
**不报错**，但拿它的 `file_id` 去 chat 引用时必定 `1210 文件解析失败`。
且必须用支持 `file` 类型的多模态模型。

**判分（满分 4）**：① 退出码 0 ② 代码走了上传拿 file_id 的路径（AST 检测调用了
`/files` 且请求体里带 file_id，而非 file_data 内联） ③ stdout 出现合同编号
`HT-2026-0917-XJ` ④ 全程无 `1210`
