## batch-best-model：模型选择的完美分离

任务是"用 Batch 批量分类，**质量要紧，用你能用的最好的模型**"。两边都认真回应了这个要求：

| | 选的模型 | 结果 |
| :--- | :--- | :--- |
| skill 版 | `glm-5.1` ×5 | 5/5 全部成功创建 batch |
| baseline | `glm-5.3` ×5 | 5/5 上传阶段即 `400 / 1210 模型名称错误` |

`glm-5.3` 是平台旗舰，看起来就是"最好的模型"——但 Batch 有一份**独立白名单**，旗舰不在其中，
而白名单里最强的是 `glm-5.1`。这条信息**只存在于报错信息里**，官方文档正文没有列出。
读了说明书的一方五次都精准挑中了白名单内的最强模型。

## pdf-reuse-fileid：静默失败的典型

任务追加了真实工程约束——"后面还要问很多轮，先上传拿 file_id 复用，别每轮重传"，
这一句堵死了 base64 内联那条绕行路线（第一版就是因为没堵，两边都绕过去了）。

| | `purpose` | 结果 |
| :--- | :--- | :--- |
| skill 版 | `user_data` ×5 | 4/5 满分；1 次失分是平台侧 `500 / 1234 网络错误`，重试三次仍失败，与知识无关 |
| baseline | `file-extract` / `agent` / 未指定 | 5/5 全部 `1210 文件解析失败` |

baseline 的失败方式特别值得看：**上传那一步全部成功**，run-1 甚至打印了 `file_id`
并贴心提示"后续运行可 export ZHIPUAI_FILE_ID 免上传"——一切信号都显示正常，
直到引用文件提问时才 400。这正是说明书里那条实测结论描述的场景。

## 为什么这轮成功而前面六个场景都打平

前面所有打平的场景，要么答案就在官方文档里、要么存在一条合法的绕行路线。
本轮两个场景同时满足三个条件，才产生了区分度：

1. **任务约束堵死了绕行**（要最好的模型 / 要复用 file_id），而这两个约束都是真实用户会提的
2. **正确答案不在文档正文里**——Batch 白名单只在报错里出现；`purpose` 的限制与 OpenAPI 规范矛盾
3. **错误是静默的或延迟暴露**——上传成功不代表能用

这个配方现在是可复用的出题方法，不是一次性的运气。

## 评分器的两次自我纠错（如实记录）

本轮判分过程中我自己写的评分器出过两个 bug，都会影响结论，都已修正并重判：

1. **把"声明不使用"误判成"使用了"**：第一版用字符串匹配 `PyPDF2|pdfplumber` 判断是否本地解析 PDF，
   结果把注释里写着"本地不做任何 PDF 解析（不用 PyPDF2）"的脚本全判违规。改为 **AST 检测真实 import**。
2. **把 batch id 里的数字误判成错误码**：用 `"1210" in output` 判断是否踩坑，
   而成功创建的 batch id `batch_2096812104876032000` 里恰好含子串 `81210` → 误扣分；
   同时另一次真实失败因报错正文未带 `1210` 字样而漏判。改为**结构化匹配** `code: 1210`
   或已知报错文案（`模型名称错误` / `文件解析失败` / `custom id 长度不足`）。

两次都是"朴素子串匹配"这一类错误。这也说明纯执行判分虽然比断言判分客观，
但**评分器本身同样需要被审查**——修正前后 batch 场景的 skill 均值从 0.933 变成 1.000。
