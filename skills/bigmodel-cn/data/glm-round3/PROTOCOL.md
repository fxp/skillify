# GLM-5.3 执行器 · 第三轮协议（开跑前冻结）

沿用第二轮验证有效的出题配方——三条同时成立才有区分度：
① 任务约束堵死绕行路线 ② 正确答案不在文档正文里 ③ 错误是静默的或延迟暴露。

条件：执行 Agent = GLM-5.3；两边都能用 WebFetch；**每配置 5 次**（n=5 才够 p<0.05）；
判分 100% 由脚本执行真实 API 决定。被测脚本用标准 Key（`ZHIPUAI_API_KEY`）。

## 场景 A · cited-web-answer（静默陷阱）

写一个联网问答脚本，回答后必须附上**真实的信息来源标题与 URL**。

**实测确认的坑（2026-09-07）**：`chat/completions` 挂 `web_search` 工具时，
不传 `search_result: true` 则响应里**根本没有 `web_search` 字段**——搜索确实执行了、
答案照常返回、HTTP 200，但你拿不到任何来源可引用。加上该字段才会返回 10 条来源。
另一条路（独立的 `/paas/v4/web_search` 端点）则要求必传 `search_engine`，
缺了直接 `1214`。**两条路各有一个坑，没有免费的绕行路线。**

**判分（满分 3）**：① 退出码 0 ② stdout 至少出现 2 条 http(s) 链接
③ 链接确实来自 API 响应（代码里读取了 `web_search` / `search_result` 数组，而非让模型自己编）

## 场景 B · rag-index-embeddings（响亮陷阱，但最自然的写法必踩）

把 `faq.txt`（150 条问题）全部用 `embedding-3` 向量化存成 `vectors.json`，
再用一句查询做 top-3 余弦检索并打印结果。

**实测确认的坑**：`embeddings` 接口 `input` 数组**一次最多 64 条**，
一把梭发 150 条直接 `400 / 1214 input数组最大不得超过64条`。

**判分（满分 4）**：① 退出码 0 ② `vectors.json` 含 150 条等长向量
③ 全程无 `1214` ④ stdout 打印了 top-3 检索结果
