# 第四轮（GLM-5.3 执行器）· 协议（开跑前冻结）

补齐纯 GLM 基准的三个缺口。条件与前三轮一致：执行 Agent = GLM-5.3、两边都能 WebFetch、
**n=5**、判分 100% 由脚本执行真实 API 决定。

## 场景 A · plan-1113-fix（补 Coding Plan 缺口）

技能最核心的差异化能力——套餐与标准 API 是两套隔离体系——此前尚未在本基准中测过。
本轮在 GLM-5.3 下重测。注入的是**真实套餐 Key**，标准 Key 不给：端点打错必然 1113。

任务：用户贴出打在标准端点、报 `429/1113` 的代码，要一份能跑通的修正版。
**判分（3）**：① 退出码 0 ② stdout 有非空模型回答 ③ 全程无 1113

## 场景 B · kb-upload-readiness（本次 review 新发现的静默陷阱）

**实测确认（2026-09-07）**：知识库上传返回 `HTTP 200` + `documentId`，看起来完全成功；
但向量化在后台失败时，检索端**持续返回 `200` + 空数组**，与"没有相关内容"无法区分。
真相只在 `GET /document/{id}` 的 `embedding_stat`（0处理中/1就绪/2失败）与 `failInfo`。
本账号实测 pdf/md/txt 三种格式均停在 `embedding_stat=2`。

任务：把 faq.txt 灌进托管知识库，并写一个校验步骤——**在告诉我"成功"之前，
必须确认文档确实已经可检索**，不可用就要明确报错。
**判分（4）**：① 退出码 0 ② 代码真的读取了 `embedding_stat`（AST/源码检查）
③ 脚本的最终结论与评分器独立查询到的真实状态一致（不可用就不能宣称成功）
④ 全程无未捕获异常

## 场景 C · async-model-pinning（本次 review 新发现的静默陷阱）

**实测确认（2026-09-07）**：`POST /paas/v4/async/chat/completions` 会静默换模型——
请求 `glm-4.6` 实际跑 `glm-4.7`，请求 `glm-4.7` 跑成文档里不存在的 `glm-4.7-ali`；
同步端点则原样透传。

任务：写异步批量脚本，因审计要求必须锁定模型版本，跑完要输出**实际使用的模型**并与请求核对，
不一致必须报警。
**判分（3）**：① 退出码 0 ② stdout 同时出现请求模型名与接口回显的实际模型名
③ 正确检出两者不一致（请求 `glm-4.6` 时必然不一致）

## 执行环境
场景 A 注入 `GLM_KEY`=套餐 Key；场景 B、C 注入 `ZHIPUAI_API_KEY`=标准 Key。每脚本超时 300 秒。
