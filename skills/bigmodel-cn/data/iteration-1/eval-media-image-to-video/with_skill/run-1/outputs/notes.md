# notes.md — image_to_video.py

## 依据

按照 `bigmodel-cn` 技能的 `SKILL.md` 导航到 `references/media.md`（图像/视频生成 + 异步轮询）
和 `references/models.md`（模型选型），字段名和 endpoint 均照抄参考文档里的表格和示例，
没有凭记忆编造。

## 做出的假设（assumptions）

1. **图片生成用同步接口，不是异步接口。** 用户描述里只明确说"视频生成是异步的，需要轮询"，
   没有要求图片也走异步。`references/media.md` 里 `glm-image` 同步接口
   （`POST /paas/v4/images/generations`）本身就支持 `glm-image` 模型（虽仅支持
   `quality=hd`，耗时约 20 秒，但依然是同步阻塞调用），比异步版本
   （`POST /paas/v4/async/images/generations`）代码更简单，所以选了同步版本。如果用户其实
   也想让图片生成走异步+轮询，需要换成 `async/images/generations` + 复用同一个
   `poll_async_result()`。

2. **首帧图片直接用 GLM-Image 返回的临时 URL 喂给视频接口的 `image_url`**，没有先下载
   到本地再转 Base64 上传。文档说图片结果 URL"有效期 30 天"，且视频接口的 `image_url`
   本来就接受 URL 或 Base64，直接传 URL 是最省事的路径。脚本仍然把图片下载到本地一份
   （方便用户留存/调试），但传给视频接口的是原始 URL，不是本地文件。

3. **首帧驱动用单个 URL 字符串，而不是 `[首帧, 尾帧]` 两元素数组。** 用户只要求"用这张图作为
   首帧"，没有提供尾帧图，所以 `image_url` 传单个字符串。文档里 `cogvideox-3` 的
   `image_url` 支持"单个 URL/Base64，或 `[首帧,尾帧]` 两张图数组"——只传首帧时用单个字符串
   是合理读法，但文档没有非常明确地写"只传首帧时该怎么传"，属于按最自然的方式推断（见下方
   "不确定"第 1 条）。

4. **`image-size` 默认取 `1728x960`（glm-image 支持的枚举值之一），`video-size` 默认取
   `1920x1080`**，两者宽高比接近（1.8 vs 1.778）但不是精确一致。文档只对 Vidu 系列的
   "首尾帧模式"明确写了"两图分辨率比例需在 0.8-1.25"这类硬性约束，对 `cogvideox-3` 的
   图生视频/首帧模式没有写类似的图片-视频分辨率匹配约束，所以没有在代码里做强校验，只是
   在默认值选择上尽量让两者比例接近，避免猜测的约束造成误导。

5. **`video-prompt` 设为可选**，因为文档写"`image_url` 与 `prompt` 不能同时为空"，即只传
   `image_url` 不传 `prompt` 也是合法请求；但为了引导生成效果，CLI 建议用户传入动作/运镜描述。

6. **API Key 环境变量名用 `ZHIPUAI_API_KEY`**，与 SKILL.md 里"30 秒跑通"示例保持一致。

7. **轮询默认参数**：间隔 5 秒、总超时 300 秒。文档只说"建议几秒一次"，没给出具体推荐值和
   超时上限，这两个数字是自己按常识定的，不是文档规定值，生产环境可能需要按视频时长/清晰度
   调整（`quality=quality` 更慢）。

8. **下载视频/图片用流式 `requests.get(..., stream=True)` 写本地文件**，文档没有专门讲
   "如何转存生成结果"，这是常规工程实践，不是接口规定的行为。

## 不确定 / 需要用户或真实调用验证的地方

1. **`image_url` 只传首帧时的写法**：文档原文是"单个 URL/Base64，或 `[首帧,尾帧]` 两张图
   数组"，没有单独给出"只有首帧、没有尾帧"的示例请求。我按最直接的理解处理成单个字符串，
   但不能 100% 排除接口实际上要求即使只有首帧也要包一层数组（如 `["url"]`）。建议第一次
   真实调用时留意报错信息，如果提示参数格式不对，尝试改成单元素数组。

2. **`fps`/`duration`/`size` 等参数是否对 `quality=speed` 模式有隐藏限制**：文档表格列出了
   取值范围，但没有说明"quality 优先"和"speed 优先"两种模式下这些参数组合是否有交叉限制
   （例如 speed 模式下是否强制 30fps）。脚本按文档字面表格暴露了完整的 CLI 选项，如果实际
   调用中某些组合被拒绝，需要以 API 实际报错为准调整。

3. **视频结果 URL 的有效期**：`media.md` 只写了图像结果 URL"有效期 30 天"，没有明确写视频
   结果 URL 的有效期。脚本假设两者类似（都需要及时下载转存），并在生成后立即下载，但没有
   在代码里对视频 URL 有效期做任何硬编码判断。

4. **错误响应体的确切结构**（`{"error": {"code", "message"}}`）是参考智谱/OpenAI 兼容接口的
   通用约定写的，`media.md`/`models.md` 本身没有给出失败响应的示例 JSON，`_parse_response()`
   里做了防御性的 `.get()` 兜底，即使实际字段名不同也不会直接抛未处理异常，但具体错误信息
   的展示可能不够精确，建议接入真实 Key 后用一次故意的错误请求（如非法 `model` 值）核实一下
   真实错误体结构。

## 未做的事（有意省略）

- 没有实现 Vidu 系列的分支（`viduq1-*`/`vidu2-*`），因为用户明确点名 CogVideoX-3。

  `BigModelAPIError` 统一抛出）。
