# 模型选择说明与不确定性

## 选了什么模型：`glm-5.1`

任务要求"最好的分类质量，预算允许"，直觉上应该选智谱当前的旗舰模型
`glm-5.3` 或 `glm-5.2`（`bigmodel-cn` 技能包 `references/models.md` 里综合推荐的
最强通用模型）。但技能包 `references/files-batch.md` 里有一条关键的、已用真实
API 调用验证过的提示：

> **Batch 只支持一份模型白名单，不是平台全部模型**。把 `.jsonl` 里的
> `body.model` 写成白名单外的模型（例如 `glm-4-flash-250414`）上传时，
> **整份文件在上传阶段就被拒绝**（业务错误码 `1210`：`模型名称错误`）。
> 实测白名单是：`glm-5.1、glm-5-turbo、glm-4、glm-4-0520、glm-4-plus、
> glm-4-long、glm-4-plus-0111、glm-4-air、glm-4-air-0111、glm-4-air-250414、
> glm-4-flash、glm-4-flashx-250414、glm-3-turbo、glm-4v、glm-4v-plus、
> glm-5v-turbo、glm-4v-plus-0111、cogview-3、cogview-3-plus、
> cogview-4-250304、embedding-2、embedding-3、cogvideox、cogvideox-2`
>
> `glm-5.3`、`glm-5.2`、`glm-image` 等旗舰模型目前都不在这份白名单里。

也就是说，"最新最强"和"Batch 能用"是两个交集很小的集合：`glm-5.3`/`glm-5.2`
虽然是更强的旗舰模型，但**根本无法用于 Batch 接口**（文件上传那一步就会直接
报错，不是创建任务时才失败）。

在确认可用的白名单里，纯文本、非视觉/非图像模型中能力最强的是 **`glm-5.1`**
（`references/models.md` 对它的定位是"编程能力对齐 Claude Opus 4.6，可自主
处理长程任务"，是白名单里明显强于 `glm-4-plus`/`glm-4-air` 等老一代模型的选
项）。因此脚本里 `MODEL = "glm-5.1"`，并且：

- 显式开启 `thinking.type: "enabled"`（glm-5.1 支持深度思考，默认由模型自动
  判断是否思考；预算允许、追求分类质量时显式打开，让模型在给结论前先做一步
  判断，而不是依赖它自己决定）。
- **没有**传 `reasoning_effort`，因为该参数按文档仅 `glm-5.2` 及以上支持，
  glm-5.1 传了可能报参数错误。
- 用 `response_format: {"type": "json_object"}` 做结构化输出（`sentiment` /
  `confidence` / `reason` 三个字段），避免情感分类结果的自由文本难以解析。
- `temperature` 设为 `0.1`（低温度），让分类结果更稳定、可复现，符合"标注/
  分类"这类偏确定性任务的常见做法。

## 我标记的不确定性

1. **这份 Batch 模型白名单不是官方正式文档发布的稳定列表**，而是技能包作者
   从一次真实 API 报错信息里摘录出来的（技能文档标注"2026-09 已用真实调用
   验证"）。白名单**随时可能因平台迭代而变化**——`glm-5.1` 今天在名单内，
   不代表未来一定还在，也不排除未来 `glm-5.3`/`glm-5.2` 被加入 Batch 支持
   范围。

2. 因此脚本没有把这份名单硬编码成一个"允许值枚举"去做本地校验，而是让
   `upload_batch_file()` 在上传失败时把服务端原始错误信息完整抛出来
   ——报错信息本身就是最新、最权威的白名单来源，比任何写死在代码/文档里的
   列表都可信。如果哪天 `glm-5.1` 也被移出白名单，报错文本会直接给出当时
   允许的模型集合，把脚本里的 `MODEL` 常量换成报错里的名字即可，不需要凭
   记忆猜测。

3. **建议实际使用前先小规模验证**：正式提交 2000 条之前，先用几条评论跑一
   遍全流程（脚本自带 `--demo` 参数，可以生成演示数据跑通"构建请求→上传→
   创建任务→轮询→下载→解析"整条链路），确认 `glm-5.1` 在你的账号/时间点
   确实能通过 Batch 文件上传校验，再对全量数据提交，避免 2000 条全部因为
   模型不在白名单里而在上传阶段整体失败。

4. `response_format: json_object` 不是数据库级别的强约束（技能文档原话：
   "平台没有类似 strict JSON Schema 的原生强约束模式"），模型仍有极小概率
   返回轻微偏离约定结构的 JSON，或者 `sentiment` 字段不严格等于"正面/负面/
   中性"三者之一。脚本的 `build_final_results()` 对解析失败、字段缺失做了
   兜底（标记 `error` 列，而不是让整个流程崩溃），最终 CSV 里可以按 `error`
   列筛出需要人工复核的行。

5. 如果后续想进一步压成本（用户提到"预算允许"，所以本版本优先质量），可以
   把 `MODEL` 换成同样在白名单里但更轻量的 `glm-4-air-250414` 或
   `glm-4-flash`（`glm-4-flash` 免费），分类质量会下降，但对情感分类这种
   相对简单的任务，差距可能没有编程/复杂推理场景那么大——如果 2000 条跑下
   来发现 `glm-5.1` 的结果已经远超预期，可以考虑用更便宜的模型做 A/B 对比，
   决定要不要降级。
