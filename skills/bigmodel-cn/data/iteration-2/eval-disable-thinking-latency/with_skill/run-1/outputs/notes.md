# 设计说明：GLM-5.3 高并发客服机器人

## 关于"关掉深度思考"这个请求

直接结论：**在 GLM-5.3 上做不到**，这不是配置疏漏，是模型层面的硬限制。

- 官方文档（`bigmodel-cn` 技能包 `references/models.md` / `references/chat.md`）明确写明：
  GLM-5.3 / GLM-5.3-Flash 是"强制思考"模型，`thinking.type` 只接受 `"enabled"`；
  显式传 `"disabled"` 会直接报业务错误码 **1210**：
  > "该模型始终思考，不支持关闭思考；请使用 low、high 或 max。"
- 能调节的只有 `reasoning_effort`，GLM-5.3 只接受三档：`low` / `high` / `max`（默认 `max`）。
- 技能包里记录了一条已用真实调用验证过的实测结果（2026-09）：同一问题下
  `reasoning_effort="low"` 时 `usage.completion_tokens_details.reasoning_tokens` 实测为 **0**，
  而 `max` 档同一问题约 800+。也就是说 `low` 档在实际效果上已经约等于"不思考"，
  只是接口层面仍然保留了 `thinking` 这个开关的壳子，不能字面意义上"关掉"。

**因此脚本里的处理方式是**：`thinking.type` 保持默认的 `"enabled"`（不传 `disabled`，
否则直接报错），把 `reasoning_effort` 设为 `"low"`，作为在"必须用 glm-5.3"前提下
能拿到的最低思考开销档位。同时把这个限制在代码注释和这份 notes 里写清楚，
不让调用方误以为脚本"成功关闭了思考"。

## 如果场景允许换模型，还有更彻底的选项

用户明确要求用 GLM-5.3，所以脚本默认保留这个模型。但如果这个客服机器人的问答
确实都是简单事实性问答（不需要复杂推理），值得权衡是否换一个模型：

- `glm-4.6`：思考行为是"模型自动判断是否思考"，可以显式传 `thinking.type: "disabled"`
  真正关闭思考（不会报错）。
- `glm-4.5-airx`、`glm-4-flashx-250414`：官方选型表里直接标注为"高并发、低延迟"场景的
  专用极速版本，价格通常也更低。
- `glm-4.7-flash` / `glm-4.5-flash` / `glm-4-flash-250414`：免费模型，如果问答质量要求不高、
  预算敏感，也是选项。

这几个模型脚本里没有默认采用，因为用户的需求描述里明确点名"用智谱 GLM-5.3"，
属于用户的既定选择，不应该在没有确认的情况下擅自换模型——但把这条路径写清楚，
方便后续按实际压测结果决定要不要切换。

## 除了思考开关之外，还做了哪些降延迟/降成本的事

思考强度只是延迟和成本的一部分，脚本里同时处理了几件同样重要、容易被忽略的事：

1. **`max_tokens` 显式设小**（默认 512，示例里用 256）。GLM-5.3 默认 `max_tokens` 是
   65536，简单问答场景完全用不到，放着不管等于让模型有权限"想生成多少生成多少"，
   显式设一个贴近实际需求的小上限，直接影响生成阶段的耗时和输出 Token 成本。
2. **连接复用**：用单个 `requests.Session` + `HTTPAdapter`（`pool_connections`/
   `pool_maxsize` 按并发度设置）复用 TCP/TLS 连接，避免高并发下每次请求都重新握手。
3. **并发度控制**：用 `threading.Semaphore` 限制同时在飞的请求数，而不是让
   `ThreadPoolExecutor` 无限并发硬冲。官方文档明确写了速率限制是按"并发请求数"算的，
   不是 QPS，对同步接口无限制地猛发并发容易直接触发限流（错误码 1302/1305）。
4. **区分错误类型再重试**：401/1210/1211 这类鉴权或参数错误重试没有意义，直接抛出；
   只有 429（1302/1305/1308/1310）和 5xx 才做指数退避 + 抖动重试，避免"重试风暴"
   加重限流（文档里明确提到过这一点）。
5. **温度调低**（`temperature=0.3`）：客服问答希望回答风格稳定、不发散，不是创造性
   任务，没必要用模型默认的较高温度。

## 没有做、但值得注意的取舍

- **没有默认开启流式输出（`stream=true`）**。对"简单问答"场景，流式主要优化的是
  "首字延迟"（用户更快看到第一个字），但会显著增加代码复杂度（SSE 解析、
  多线程下每个连接要单独维护一个生成器）。当前脚本用同步整体返回 + 线程池并发，
  优先保证吞吐和代码可维护性；如果产品体验上需要打字机效果，参考技能包
  `references/chat.md` 第三节的 SSE 消费写法（用标准库 `requests` 按行解析
  `data:` 前缀 + `[DONE]` 终止符）改造 `ask()` 即可，属于低成本的后续增强。
- **没有接入上下文缓存优化**。技能包 `references/chat.md` 第七节提到平台会对完全
  相同的 `system` 提示词自动做隐式缓存（命中部分按半价计费）。脚本里的 `system_prompt`
  在同一个 `SupportBotClient` 实例内是固定不变的，理论上天然满足触发缓存的条件，
  但缓存命中率、时效性由平台侧决定，代码层面无法保证，也没有接口可以主动查询/预热，
  只能观测 `usage.prompt_tokens_details.cached_tokens` 做事后分析，没有写进本脚本的
  "设计承诺"里，只作为一个已知的潜在优化点记录。

## 不确定 / 需要用户或实测确认的点

- **具体并发上限**：技能包明确写"速率限制按用户权益等级 × 模型独立设置并发池上限，
  无法通过 API 查询"，脚本里 `max_concurrency=20` 是一个保守的示例默认值，
  实际值需要用户登录控制台（`https://bigmodel.cn/usercenter/proj-mgmt/rate-limits`）
  查看后调整，不能假设它对所有账户都适用。
- **价格**：技能包明确要求不要在代码/文档里硬编码价格（模型仍在持续迭代），
  所以本 notes 没有给出具体每 Token 单价，需要用户自己去
  `https://bigmodel.cn/pricing` 核实 `reasoning_effort="low"` 相对
  `max` 档的实际成本差异幅度。
- **`reasoning_tokens=0` 是否是所有问题类型下的普遍表现**：技能包里的实测只针对
  "同一个问题"做了 low vs max 的对比，没有覆盖客服场景可能遇到的各种问题类型
  （比如涉及多轮上下文、需要一定推理的复杂咨询）。如果实际压测中发现某些问题类别
  在 `low` 档下回答质量明显下降，属于预期内的权衡（低思考强度本来就会牺牲部分
  复杂任务的准确性），需要用户根据自己的问答样本实测验证，而不是假设 `low`
  在所有问题上都零质量损失。
- **本脚本未实际调用 bigmodel.cn API**（按任务要求，环境中没有配置真实 Key，
  也不应该配置）。所有关于延迟/Token 消耗的数字均来自技能包里记录的、
  技能作者此前用真实调用验证过的结果，不是本次运行现场测出来的，代码逻辑本身
  已做过 `py_compile` 语法检查和无 Key 情况下的空跑（确认没有发起真实网络请求），
  但请求体字段的最终有效性仍建议用户拿到真实 Key 后自行跑一次做验证。
