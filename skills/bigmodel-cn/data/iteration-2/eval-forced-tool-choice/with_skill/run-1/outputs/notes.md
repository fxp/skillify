# 设计说明：如何保证 lookup_order 一定会被调用

## 核心问题

需求是「不管用户说什么，都必须先调用 `lookup_order(order_id)`，绝对不能让模型
跳过这一步直接自由回答」。这是一个**强制工具调用（forced tool choice）**的需求。

## 关键限制（来自 `bigmodel-cn` 技能包 `references/chat.md` 第四节）

> `tools` 最多 128 个函数；**`tool_choice` 目前默认且仅支持字符串 `"auto"`
> （不支持强制指定某个函数）**。

也就是说，智谱 GLM 的 `chat/completions` 接口**没有** OpenAI 那种
`tool_choice: {"type": "function", "function": {"name": "lookup_order"}}`
式的服务端强制机制。如果只是把 `lookup_order` 注册成一个 tool，然后指望
`tool_choice="auto"` + 一句系统提示词让模型"自觉"调用它，模型完全可能对
"你好""今天星期几"这类无关问题直接用自然语言回答，跳过工具调用——这正是
需求明确禁止的行为，也是纯 prompt 层面无法给出硬保证的地方。

## 设计决策：把"强制"下沉到应用层代码，而不是依赖模型/API 参数

`order_bot.py` 的做法是：**每一轮用户消息进来后，代码在把消息交给模型之前，
无条件、同步地直接调用真正的 Python 函数 `lookup_order(order_id)`**，完全不
经过模型的"决策"。调用结果随后被手工拼装成一轮标准的 function-calling
消息对（`{"role": "assistant", "tool_calls": [...]}` 紧跟
`{"role": "tool", "tool_call_id": ..., "content": ...}`），追加进对话历史。
只有当这份真实查询结果已经写入历史之后，代码才第一次把完整消息列表发给
GLM-5.3 去生成自然语言回答。

关键在于：**模型永远不会被置于"要不要调用工具"的十字路口**——它压根没有
"不调用直接回答"这个分支可选，因为在它第一次被调用之前，工具调用这件事
已经在 Python 控制流里无条件发生了。这是比"死磕 API 强制参数"或"死磕
prompt 措辞"更可靠的工程手段：正确性由 `if/for` 控制流保证，而不是由模型
的"服从度"保证。

对应代码位置：
- `OrderBot.handle_user_message()`：每次用户发消息，第一步永远是
  `self._force_lookup_order(current_order_id)`，之后才调用
  `self._run_model_turn()` 去请求模型。
- `OrderBot._force_lookup_order()`：真正执行 `lookup_order()`，并把结果
  写成合规的 assistant/tool 消息对。

`tools` 里仍然注册了 `lookup_order` 的 JSON Schema，`tool_choice` 仍然传
`"auto"`（这是唯一合法值）——但这只是为了让模型在**后续轮次**里，如果用户
在对话中途报出一个新订单号，模型可以（可选地）自己再发起一次调用；脚本的
`_run_model_turn()` 循环会照常真实执行并把结果写回。这个"可选的模型自主
调用"和"第一步的强制调用"是两回事，不要混淆：强制调用保证下限（每轮至少
查一次），模型自主调用只是锦上添花，不承担任何"保证"职责。

## 关于订单号从哪里来

一个客服工单在业务上通常本来就绑定着某个订单，所以 `OrderBot(order_id=...)`
在创建时可以直接带上工单关联的订单号；每一轮如果用户新提到了一个能匹配
订单号格式的字符串（`extract_order_id()`，正则尽力而为），就切换成查询那个
新订单号，否则继续用工单默认绑定的订单号。即使一个订单号都识别不出来
（`order_id` 为空/`UNKNOWN`），`_force_lookup_order` 依然会被无条件调用，
只是 `lookup_order()` 返回 `{"found": false, "error": "..."}`，交给模型去
礼貌地追问用户要订单号——「调用这件事一定发生」和「调用参数是否完整」是
两个独立的保证维度，本设计只对前者做硬保证，后者是最佳努力（best-effort）。

## 已用代码验证过的行为

用占位 key 实际跑过 `OrderBot.handle_user_message("你好，今天星期几呀")`
（一句和订单完全无关的问题）：在真正发起（并按预期失败于 401，因为没有
真实 key）HTTP 请求之前，`bot.messages` 里已经确定性地包含了完整的
assistant `tool_calls` + `tool` 结果这一对消息，证明"强制调用"发生在网络
请求之前、且与用户说了什么无关。

## 未解决的不确定性 / 需要使用方注意的点

1. **本设计保证"调用一定发生"，不保证"模型一定会采纳/复述工具结果"。**
   模型看到 `tool` 消息后仍有可能在最终回答里不提订单状态（例如答非所问）。
   这是 prompt 质量问题，已经通过 `SYSTEM_PROMPT` 里的显式约束尽量降低
   概率，但不是代码结构性保证的范围；如果业务上要求"回答里必须包含订单
   状态字段"，建议再加一层输出校验/正则检查，必要时拒绝返回给用户重新生成。
2. **`lookup_order` 目前是本地 mock**（题目要求不真实调用外部接口）。生产
   环境替换为真实订单服务调用时，注意异常处理（超时、5xx、订单不存在）
   都要在 `lookup_order()` 内部转换成结构化的 dict 返回给模型，而不是让
   异常直接抛出中断整个对话流程。
3. **订单号提取用的是通用正则**（`[A-Za-z]{1,4}-?\d{6,15}` 或纯数字兜底），
   没有对接真实的订单号命名规则，存在误识别/漏识别的可能；这不影响"是否
   调用"这个核心保证，只影响调用时传的 `order_id` 参数是否精确。
4. **`tool_stream`（工具调用参数流式返回）未使用**，因为本设计里第一次
   调用是代码直接构造的，不涉及"等待模型流式吐出 arguments"的场景；如果
   后续要支持模型自主发起的第二轮工具调用做流式体验，可以在
   `_run_model_turn()` 里参照 `references/chat.md` 第三节补充 SSE 处理，
   目前用的是同步（非流式）请求，逻辑更简单、也更容易保证正确性。
5. 未对真实 API 的错误响应体（如 `{"error": {"code": ..., "message": ...}}`
   结构）做精细化解析，只用了 `resp.raise_for_status()` 触发
   `requests.HTTPError`；生产环境建议解析 `error.code` 做针对性重试/降级
   （参考 `references/errors-and-limits.md`，本次任务未要求读取该文件，
   故未展开实现）。
