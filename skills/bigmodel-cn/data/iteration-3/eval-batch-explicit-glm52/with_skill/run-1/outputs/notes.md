# 关于模型选型：为什么没有直接用 GLM-5.2

用户明确要求"就用 GLM-5.2 模型吧"，理由是团队其他项目统一用这个模型。但在写代码前，
按技能包指引查阅了 `bigmodel-cn/references/files-batch.md` 里 Batch API 的说明，发现一条
明确标注"已用真实调用验证"的关键限制：

> **⚠️ Batch 只支持一份模型白名单，不是平台全部模型**。把 `.jsonl` 里的 `body.model`
> 写成白名单之外的模型（例如旗舰模型 `glm-5.3`、`glm-5.2`、`glm-image` 等），**整份文件
> 在上传阶段（`POST /paas/v4/files`）就会被拒绝**，业务错误码 `1210`："模型名称错误"。
>
> 截至验证时的白名单：`glm-5.1、glm-5-turbo、glm-4、glm-4-0520、glm-4-plus、glm-4-long、
> glm-4-plus-0111、glm-4-air、glm-4-air-0111、glm-4-air-250414、glm-4-flash、
> glm-4-flashx-250414、glm-3-turbo、glm-4v、glm-4v-plus、glm-5v-turbo、glm-4v-plus-0111、
> cogview-3、cogview-3-plus、cogview-4-250304、embedding-2、embedding-3、cogvideox、
> cogvideox-2`

`glm-5.2` 不在这份白名单里。也就是说，如果按用户字面要求把 `glm-5.2` 写进 2000 条请求的
`.jsonl` 文件，**根本走不到"创建批处理任务"这一步**——文件上传阶段就会被整体拒绝，2000
条评论一条都跑不了，用户在拉取结果之前才会看到 API 报错。这不是"能跑但效果打折"，而是
"跑不通"，所以没有按字面意思实现，而是做了替换。

## 实际选用的模型：`glm-4-air-250414`

在白名单范围内挑选，考虑因素：

- **任务复杂度**：情感分类（正面/负面/中性）是一个简单的短文本分类任务，不需要旗舰模型
  的长上下文、复杂推理或 Agent 能力，`glm-4-air-250414` 这类轻量模型完全够用。
- **成本**：用户的诉求本来就是"节省成本"，Batch 价格已经是标准 API 的 50%，再叠加一个
  轻量模型，比强行凑一个进不了白名单的旗舰模型更贴合诉求本身。
- **白名单确定性**：`glm-4-air-250414` 明确出现在技能包记录的真实报错白名单里，可信度高
  于凭经验猜测其他模型是否被支持。

脚本里把模型代码集中放在 `MODEL` 常量（`batch_sentiment.py` 顶部配置区），如果用户的账号
后续确认 `glm-5.2`（或其他型号）已经被加入 Batch 白名单——名单本身会随平台迭代变化，技能
包也提示"报错信息本身就是最权威的来源"——只需要改这一行常量即可切换，不需要改动上传 /
创建任务 / 轮询 / 下载 的任何逻辑。**强烈建议**在改动后先用几条测试数据跑一次
`--dry-run` 之外的真实小批量（比如 5-10 条），确认文件上传不报 1210 错误，再提交完整的
2000 条，避免整份任务失败。

## 其他需要用户知道的取舍

- 2000 条评论远低于 Batch 单文件 50,000 条 / 100MB 的限制，不需要拆分成多个文件。
- `custom_id` 使用 `review-{review_id}` 格式，确保不短于官方要求的 6 个字符（技能包记录了
  实测报错：传 `r1` 这种两三位短字符串会在文件上传阶段直接报错 `1210`）。
- 脚本要求输入是一个 CSV 文件（`review_id,review_text` 两列，`review_id` 可省略自动编号），
  没有真实的 2000 条评论数据，所以脚本本身不内置示例数据，而是通过 `--input` 参数接收用户
  自己的评论文件；提供了 `--dry-run` 模式，可以在没有真实 API Key 的情况下先在本地生成并
  检查 `.jsonl` 请求文件格式是否正确（已用 3 条示例数据实测跑通，未发起任何真实网络请求）。
- 情感标签固定为"正面/负面/中性"三分类，通过 system prompt 约束模型只输出标签本身，便于
  用简单字符串匹配解析结果，避免依赖尚未在 Batch 场景验证过的结构化输出（JSON mode）字段。
