# 设计说明：GLM-5.2 高并发客服机器人的“关思考”决策

## 结论先行

对 **glm-5.2** 而言，深度思考（thinking）不是强制开启的，可以用请求参数
**显式关闭**：

```json
"thinking": {"type": "disabled"}
```

这是本次代码的核心优化点，直接对应用户的问题“能不能关掉深度思考模式来提速省钱”——对
glm-5.2，答案是**能**，而且应该关。

## 为什么这一点必须按模型版本单独核实（关键的版本差异）

技能包 `bigmodel-cn/references/models.md` 和 `references/chat.md` 里明确给出了一张
按模型区分的 thinking 行为表，几个 GLM-5.x 型号的行为**并不一致**：

| 模型 | thinking 默认行为 | 能否关闭 |
| :-- | :-- | :-- |
| `glm-5.3` / `glm-5.3-flash` | **强制开启**，只能用 `reasoning_effort`（仅 `low`/`high`/`max`）调节强度 | **不能关闭**，传 `thinking.type: "disabled"` 会直接报业务错误码 `1210`（"该模型始终思考，不支持关闭思考；请使用 low、high 或 max"） |
| `glm-4.7` / `glm-4.5v` | 强制思考 | 不能关闭 |
| **`glm-5.2`**（本任务用的模型）/ `glm-5.1` / `glm-5` / `glm-5-turbo` / `glm-4.6` / `glm-4.5` 等 | 模型自动判断是否思考 | **可以**用 `thinking.type` 显式开关 |
| `glm-4.5` 以下版本 | 不支持 `thinking` 参数 | 不适用 |

也就是说，如果我不核实模型版本、直接照抄网上或旧文档里针对 glm-5.3 的“思考没法关，只能调
`reasoning_effort`”这类结论，会在 glm-5.2 上得出错误的、次优的方案（比如退而求其次只把
`reasoning_effort` 调到 `none`/`minimal`，而不是直接彻底关闭）。反过来，如果把本脚本里
`thinking.type: "disabled"` 的写法原样套到 glm-5.3 上，会直接触发接口报错，线上请求会
100% 失败。**这是本任务里最容易踩的坑，代码注释里也重复强调了一遍。**

## 具体决策与取舍

1. **`thinking: {"type": "disabled"}`**：对 glm-5.2 直接彻底关闭思考，而不是退而求其次
   调 `reasoning_effort`。原因：
   - 关闭后模型不会生成 `reasoning_content`，节省的是**思考过程本身消耗的
     completion token**（这部分通常比最终答案本身贵得多，尤其对"你好""我的订单在哪儿"
     这类根本不需要推理的问题）。
   - 关闭思考也直接降低了首字延迟——不用等模型先"想"一遍再作答。
   - 没有一并传 `reasoning_effort`：技能包明确写了这个参数"仅在 thinking 开启时生效"，
     thinking 已经关闭的情况下传它没有意义，容易造成"这个参数到底生不生效"的误解，所以
     干脆不传。

2. **`max_tokens=512`（可调）**：简单问答不需要很长的回复，显式设置输出上限，防止模型
   意外跑题写成长文，同时也是成本的硬保险（即使某次没触发"该关的思考"逻辑，输出长度
   仍然有上限兜底）。

3. **`do_sample=False`（贪心解码）**：客服场景更看重回答的稳定性和可复现性，而不是
   创造性；顺带也省去了 `temperature`/`top_p` 的调参心智负担。这是一个偏保守的默认值，
   如果产品希望语气更"有变化"，可以改回 `do_sample=True` + 较低的 `temperature`（如
   0.3），代价是可复现性下降，成本/延迟影响很小。

4. **非流式（`stream=False`）**：客服简答通常很短，流式带来的"打字机效果"和更低的
   首字感知延迟，对几十字的回答收益有限，却会显著增加高并发场景下的代码复杂度（SSE
   解析、更长的连接占用时间）。这是本次为了"简单问答 + 标准库 requests 可运行脚本"
   这个具体需求做的取舍，**不是通用结论**——如果客服回答变长，或者产品明确要逐字显示，
   应该改成流式并按 `references/chat.md` 第三节解析 `data:` 行、检查每个 chunk 的
   `finish_reason`。

5. **并发控制用信号量 + 连接池，而不是无限开线程**：技能包 `errors-and-limits.md`
   明确指出智谱的限流是按"同时处理中的并发请求数"计算的，不是 QPS。所以脚本里用
   `threading.Semaphore(max_concurrency)` 把同时在途的请求数钳制住，并把
   `requests.Session` 的连接池大小设成同一个值，避免连接数成为新瓶颈。`max_concurrency`
   的具体数值需要用户自己去控制台 `https://bigmodel.cn/usercenter/proj-mgmt/rate-limits`
   查看账户在 glm-5.2 上的并发额度，代码里给的 `20`/`5`（demo 用）只是占位默认值，
   **不代表真实额度**。

6. **重试策略区分错误类型**：只对 429 类（业务错误码 1302/1305/1308/1310）和 5xx 做
   指数退避 + 抖动重试；401/403/400 类判定为参数或鉴权问题，直接抛出不重试——这是
   `errors-and-limits.md` 里明确给的建议（固定间隔的高频重试会加重限流，纯参数错误
   重试也没有意义）。

7. **system prompt 固定成模块级常量、不逐次拼接改写**：bigmodel.cn 的上下文缓存是隐式
   自动生效的，只要多次请求里重复的前缀（典型是 system prompt）保持完全一致，就有机会
   命中缓存、降低这部分的计费与耗时。所以没有把 system prompt 做成运行时可变参数。

## 尚存的不确定性 / 需要用户自行验证的地方

- **`thinking.type: "disabled"` 在 glm-5.2 上的真实省钱幅度没有做过实测**。技能包里对
  glm-5.3 的 `reasoning_effort: low` vs `max` 有过真实 API 调用验证（`low` 档
  `reasoning_tokens` 实测为 0），但**没有**给出 glm-5.2 在 `thinking.type: disabled` 时
  的实测 token/延迟对比数据。本任务按要求没有用真实 Key 调用 API，所以这一点是基于文档
  描述的合理推断，不是实测结论——建议用户拿到真实 Key 后，用同一批问题分别测一下
  "`thinking: {"type": "disabled"}`" 与默认（模型自动判断是否思考）两种配置下的
  `usage.completion_tokens` 和端到端耗时，确认收益是否符合预期。
- **`max_concurrency` 的默认值（20，demo 里是 5）是占位值**，不是从账户额度或压测得出的
  推荐值。用户接入真实流量前，必须去控制台核实自己账户在 glm-5.2 上的并发额度，并结合
  真实压测调整这个数字，否则要么浪费并发额度（设太小），要么频繁触发限流错误码 1302
  （设太大）。
- **`do_sample=False` 是否符合产品语气要求没有和用户确认**——贪心解码换来的是稳定性，
  代价是回答可能显得比较"机械"。如果产品希望客服语气更自然/有变化，这里需要改回
  `do_sample=True` 并调低 `temperature`，是一个产品侧而非技术侧的取舍，本次按"响应速度
  和成本优先"的需求描述做了偏保守的默认选择。
- **脚本未经真实 API Key 验证**——按任务要求没有调用真实 bigmodel.cn 接口（没有可用
  Key），已用 mock 请求验证了参数拼装、payload 结构、重试/错误分支的代码逻辑是自洽可运行
  的，但响应体的真实字段/边界情况（例如触发内容安全审核、prompt 超长等）仍需要用真实
  Key 跑一遍做最终确认。
