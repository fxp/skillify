# Coding Plan 校准轮协议（开跑前冻结）

重测 Round 6（GLM Coding Plan，原口径 100% vs 71%）里最核心的两条断言。
条件与 `../recalibration/PROTOCOL.md` 一致：**两边都允许联网**、**每配置 3 次**、
**判分 100% 由脚本执行真实 API 的结果决定**。

唯一注入的环境变量是 `GLM_KEY`，值为**真实的 GLM Coding Plan 套餐 Key**。
标准 Key 不注入——这正是要测的：脚本必须打对端点才能跑通。

## 场景 A · plan-1113-fix

用户贴出一段打在标准端点、报 `429 / 1113 余额不足` 的代码，要一份能跑通的修正版。
这是 Round 6 里最核心的一条主张："1113 不是余额问题，是端点问题"。

**判分（满分 3）**：
1. 脚本退出码为 0
2. stdout 有非空的模型回答（不是报错栈）
3. 全程未出现 `1113`（stdout / stderr 里都不能有）

## 场景 B · plan-longdoc-model

用套餐额度给一份长文档做摘要。真实约束：套餐只覆盖部分模型——实测 `glm-4-long`、
`charglm-4`、`codegeex-4` 用套餐 Key 调用会返回 `1113`，而 `glm-5.3`、`glm-5.3-flash`
以及若干免费模型可用。给长文档做摘要时，`glm-4-long` 是个自然但错误的选择。

**判分（满分 3）**：
1. 脚本退出码为 0
2. stdout 有非空摘要（≥ 50 字），且不是报错栈
3. 全程未出现 `1113`

## 执行环境

每个脚本超时 300 秒，工作目录内提供 `report.txt`（2596 字）。
Key 只经环境变量注入，不写入任何文件；评分器对输出做 Key 脱敏。
