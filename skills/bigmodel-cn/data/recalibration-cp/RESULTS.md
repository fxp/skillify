# Coding Plan 校准轮结果（2026-09-04）

重测 Round 6（原口径 100% vs 71%）里最核心的两条断言。条件与 `../recalibration/` 一致：
两边都允许联网、每配置 3 次、判分 100% 由脚本执行真实 API 决定。判分标准开跑前冻结于 `PROTOCOL.md`。
注入的是**真实的 Coding Plan 套餐 Key**，标准 Key 不给——端点打错就必然 1113。

## 结果：两个场景都是完全打平

| 场景 | Round 6 口径 | skill | baseline |
|---|---|---|---|
| plan-1113-fix（套餐 Key 报 1113，要能跑通的修正版） | 100% vs 60% | **1.000 ± 0.000** | **1.000 ± 0.000** |
| plan-longdoc-model（用套餐额度做长文档摘要） | 100% vs 80% | **1.000 ± 0.000** | **1.000 ± 0.000** |

12 次执行全部 3/3，耗时 5.5–16.3 秒，没有一次出现 `1113`。

## 为什么打平

**端点这条知识在官方文档里，一搜就有。** 三个 baseline 全部靠联网找到了
`https://open.bigmodel.cn/api/coding/paas/v4`，并且各自引用了官方页面
（`coding-plan/tool/others`、`coding-plan/quick-start`、`coding-plan/overview`、`coding-plan/latest-model`）。
六个脚本实际请求的都是 Coding 端点，`/api/paas/v4` 只出现在它们的解释性注释里。

**模型选择也没有踩坑。** 长文档摘要这个场景本来预期 baseline 可能会顺手选 `glm-4-long`
（1M 上下文、名字就写着"long"，但实测用套餐 Key 调用会返回 1113）。实际三个 baseline
全部选了 `glm-5.3`，理由都是"1M 上下文，套餐内"。没有一个掉进去。

**baseline 甚至提出了一条我们的说明书没强调的风险。** `plan-longdoc-model/without_skill/run-2`
指出官方文档把"自建应用/脚本通过 API 集成"排除在套餐额度之外，因此自写脚本很可能按标准 API 计费，
并为此提供了切换到标准入口的开关。这比单纯"能跑通"更接近生产上该考虑的问题。

## 这一轮能证明什么

**能证明的**：Round 6 的 `100% vs 60~80%` 在对称条件下不成立。这两个场景所依赖的知识
（Coding 端点、套餐内模型）**都是公开文档里查得到的**，baseline 联网后 6/6 全部答对。

**必须说清的选择偏差**：这两个场景是按"真实用户会怎么问"设计的，我**刻意没有**围绕
说明书里那些实测得来、官方文档没写的结论去出题——比如"标准 Key 其实也能打 Coding 端点"、
"`glm-4.6`/`glm-4.5-air` 会被静默路由成 `glm-5.3-flash`"、"`thinking:disabled` 在标准端点
报 1210 但在 Coding 端点生效"、"同一个 1113 有端点/能力/模型三种成因"。
围绕这些出题几乎必然是 skill 赢，但那等于拿着答案去设计考卷，不能算证据。
**这类知识的价值目前没有被这轮测到，也不该被这轮的打平否定。**

| 场景 | 原口径 | 校准后 skill | 校准后 baseline |
|---|---|---|---|
| forced-tool-call | 100% vs 40% | 1.000 | 1.000（平） |
| json-extraction | 100% vs 40% | 1.000 | 0.667 ± 0.471 |
| plan-1113-fix | 100% vs 60% | 1.000 | 1.000（平） |
| plan-longdoc-model | 100% vs 80% | 1.000 | 1.000（平） |

24 次执行：skill 12/12 全部满分，baseline 11/12。唯一那次失败是忘了关思考导致超时，
与 Coding Plan 无关。**在允许联网、纯执行判分、n=3 的条件下，这四个场景没有一个能复现
原报告的差距量级；skill 版的优势主要体现为零方差（12/12 稳定），而不是 baseline 会失败。**
