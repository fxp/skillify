# v3 · 准确率提升轮 · 协议（开跑前冻结）

## 目的

v2 在既有 8 个场景上已经打到 39/40 的天花板，**没有提升空间**。
本轮专门挑 **v2 覆盖薄弱、且预期会失败**的四个新场景，先测出 v2 的真实空间，
再据此改进说明书（v3），用同一套冻结标准复测。**只有 v3 显著高于 v2 才算达成目标。**

## 口径

执行 Agent = **GLM-5.3**（Claude Code CLI 仅作 harness）；两侧都能 WebFetch；
Agent 写代码时拿不到 Key；判分 100% 由评分器用真实 Key 执行生成脚本决定。
**n = 5**，4 场景 × 5 = 20 次运行 / 每个说明书版本。

v2 与 v3 用**完全相同的任务文本、harness 与评分器**，唯一变量是说明书。

## 四个坑（开跑前 2026-09-08 逐个真实探针确认）

| 场景 | 实测事实 |
| :--- | :--- |
| `tts-asr-roundtrip` | TTS 默认返回 **`content-type: audio/pcm`**，前 4 字节不是 `RIFF`（裸 PCM）。ASR 只收 wav/mp3。必须显式 `response_format: "wav"` 才拿到 RIFF |
| `plan-vision-ocr` | 文档称 Coding Plan 只含 `glm-5.3`/`glm-5.3-flash`，**实测 `glm-4.6v`、`glm-5v-turbo` 在套餐端点可用**；而 `glm-4.6` 被**静默换成 `glm-5.3-flash`** |
| `rerank-restore-docs` | `POST /rerank` 的 `results` 每项**只有 `index` 和 `relevance_score`，没有文档原文**。取 `results[i]["document"]` 直接 KeyError |
| `long-cited-answer` | 带引用的长回答容易撞 `finish_reason: length`（思考 token 计入 `max_tokens`）。**v2 实测就栽在这里**：脚本正确检测到了却直接退出，没有加预算重试 |

## 场景与冻结判分标准

### 1. `tts-asr-roundtrip`
**任务**：合成一句话语音存到本地，再用平台 ASR 把它转写回来，打印转写文本并与原文比对确认链路通了。

| # | 判分项 | 通过条件 |
| :-: | :--- | :--- |
| 1 | 无未捕获异常 | 无 `Traceback` |
| 2 | 落盘的音频是真 WAV/MP3 而不是裸 PCM | 工作目录里存在音频文件且首 4 字节为 `RIFF` 或 `ID3`/MPEG 帧头 |
| 3 | **ASR 真的转写出了内容** | 输出中出现与原文重合的中文片段（≥3 个连续汉字命中） |
| 4 | 脚本自己做了比对并给出结论 | 输出出现"一致/匹配/成功/相符"之类的比对结论，且第 3 项通过 |

### 2. `plan-vision-ocr`
**任务**：只有 Coding Plan 套餐 Key，用套餐额度识别同目录 `invoice.png` 里的内容；若套餐不支持视觉要明确说明。

| # | 判分项 | 通过条件 |
| :-: | :--- | :--- |
| 1 | 无未捕获异常 | 无 `Traceback` |
| 2 | **真的调通了视觉模型**（没有错误地断言"套餐不支持视觉"） | 输出里有模型对图片的描述性回答，且不出现"套餐不支持视觉/无法识别图片"之类的放弃结论 |
| 3 | 用的是套餐端点 | 代码中出现 `coding/paas/v4` 或 `api/anthropic` |
| 4 | 打印了服务端回显的实际模型名 | 输出出现 `glm-` 开头的模型名 |

### 3. `rerank-restore-docs`
**任务**：用 rerank 给 5 段候选文档排序，输出**排序后的文档原文**与分数（不是序号）。

| # | 判分项 | 通过条件 |
| :-: | :--- | :--- |
| 1 | 无未捕获异常 | 无 `Traceback` |
| 2 | **输出了文档原文而不是序号** | 输出中出现 ≥3 段候选文档的原文片段 |
| 3 | 输出了相关性分数 | 输出出现 0–1 之间的小数 |
| 4 | 排序正确（最相关的排第一） | 输出里第一条是与 query 最相关的那段 |

### 4. `long-cited-answer`
**任务**：联网问答，答案要**完整**（明确要求不能被截断），并给出至少 2 条可点击来源链接。

| # | 判分项 | 通过条件 |
| :-: | :--- | :--- |
| 1 | 无未捕获异常 | 无 `Traceback` |
| 2 | **答案完整未被截断** | 输出不以 `finish_reason=length` 收场；若检测到截断必须已重试并最终拿到完整答案 |
| 3 | **至少 2 条 http(s) 来源链接** | 输出出现 ≥2 个 `http(s)://` |
| 4 | 来源取自接口返回而非模型编造 | 代码中读取了 `web_search` / `search_result` 数组 |

## 事前声明

- 判分标准以本文件为准，v2 与 v3 用同一份，跑完不改。
- 若发现评分器 bug，**修正后 v2/v3 一起重判**并如实记录涨跌。
- 只有 **v3 显著优于 v2**（Fisher p < 0.05）才算达成"准确率有所提升"；
  同时 token 不得高于 v2，否则同样不算达成。

# 补充协议 · 硬场景轮（2026-09-08，开跑前冻结）

## 为什么加这一轮

前五个场景 v2 与 v3 都是 **23/25 满分**——GLM-5.3 配上一份好说明书已经接近天花板，
n=5 在 92% 满分率上撑不起显著性。但第一轮暴露出一个明确的失败模式：
**脚本正确检测到了问题，然后直接退出，把半截结果丢给用户**
（v2 `long-report-complete/run-1` 正文 0 字；`long-cited-answer/run-4` 截断且 0 条链接）。

v3 的核心改动正是针对它：新增「撞上了怎么补救」一节。
**本轮三个场景专门把运行时故障做成必然事件**，检验这个假设。
假设在看到第一轮结果之后形成，但**在跑本轮之前**固定，用的是全新数据。

## 三个硬场景（判分标准冻结）

### H1 `tight-budget-complete`
**任务**：下游接口有硬限制，**单次请求 `max_tokens` 不得超过 1000**；但要拿到一份 ≥600 汉字的完整正文。
**为什么必然触发**：实测 `glm-4.6` 写这类正文，思考链要 2400+ token。
`max_tokens=800` → 正文 **0 字**；1500 → 289 字仍截断。
**在 ≤1000 的约束下，只有关掉思考（实测正文 1388 字）或分段生成再拼接才能完成。**

| # | 判分项 | 通过条件 |
| :-: | :--- | :--- |
| 1 | 无未捕获异常 | 无 `Traceback` |
| 2 | 正文 ≥600 汉字 | 输出汉字数 ≥600 |
| 3 | 遵守了 `max_tokens ≤ 1000` 的约束 | 代码中所有 `max_tokens` 取值均 ≤1000 |
| 4 | 没有把截断的半截内容丢出来 | 第 2 项通过，或明确说明未达标而非佯装完成 |

### H2 `batch-forced-flagship`
**任务**：用户**点名要用 `glm-5.3` 跑 Batch**（"要最好的"）。
**为什么必然触发**：`glm-5.3` 不在 Batch 白名单，上传阶段必定 `1210 模型名称错误`。
正确行为是**检测到之后自动降级到白名单内最强的模型并跑通**，同时告知用户为什么换。

| # | 判分项 | 通过条件 |
| :-: | :--- | :--- |
| 1 | 无未捕获异常 | 无 `Traceback` |
| 2 | **最终真的创建成功了 batch** | 输出出现 `batch_` 开头的任务 id |
| 3 | 没有卡在 `1210` 上退出 | 不存在"报了 1210 且没有成功 id"的情况 |
| 4 | 向用户说明了为什么换模型 | 输出提到白名单/不支持/已改用 之类的说明 |

### H3 `kb-fallback-when-vectorize-fails`
**任务**：把一份 FAQ 灌进托管知识库并**确保能检索到**；如果知识库这条路走不通，
**要给我一个真的能用的替代检索方案**，不是只报错。
**为什么必然触发**：该测试账号的向量化实测经常落在 `embedding_stat=2`（`知识不可用，文档损坏`）。

| # | 判分项 | 通过条件 |
| :-: | :--- | :--- |
| 1 | 无未捕获异常 | 无 `Traceback` |
| 2 | 检查了 `embedding_stat` 而不是假设上传即可用 | 代码中出现 `embedding_stat` |
| 3 | **最终真的能检索**（托管知识库成功，或降级方案真的跑出了检索结果） | 输出中出现与 FAQ 原文重合的检索结果片段 |
| 4 | 结论诚实（不可用时不谎称成功） | 不存在"没有任何检索结果却宣称成功" |

## 事前声明

- v2 与 v3 用**完全相同**的任务文本、harness 与本判分标准，n=5。
- 判分标准以本节为准，跑完不改。发现评分器 bug 则**两版一起重判**并如实记录。
- 达成标准：**v3 满分率显著高于 v2（Fisher p < 0.05）且 token 不高于 v2**。
