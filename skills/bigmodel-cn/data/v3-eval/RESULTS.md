# v3 · 准确率提升尝试 · 结果（2026-09-08）

## 结论：**v3 不予采用。目标的「准确率提升」这一半，在现有证据上做不到。**

| | 满分率 | 平均分 | 线上 token | 计费当量 |
| :--- | ---: | ---: | ---: | ---: |
| v2（现行） | **37/40** | 0.969 | 467,202 | **142,707** |
| v3（本轮尝试） | 35/40 | 0.963 | 446,591 (−4.4%) | 148,301 (**+3.9%**) |

满分率 Fisher 双尾 **p = 0.71**；逐次得分 Mann-Whitney **p = 0.73**。
**v3 名义上更差，且计费当量更高——两个达成条件都不满足，因此不上线，`bigmodel-cn` 保持 v2。**

## v3 改了什么

针对第一轮观察到的失败模式——**脚本正确检测到问题后直接退出，把半截结果丢给用户**——
在 SKILL.md 里加了「撞上了怎么补救」一节（8 条运行时补救路径），
并补了 3 条新实测陷阱（TTS 默认裸 PCM、rerank 分数压缩到并列 1.0、套餐下视觉模型实际可用）。
同时削掉冗余，把常驻成本从 +3,360 压到 **+1,204 字节**。

假设是合理的，改动也确实命中了它想修的地方——`tight-budget-complete` 从 4/5 变 **5/5**——
但其他场景的随机波动把这点收益抵消掉了。

与说明书无关。这是 n=5 在高满分率下的正常波动。

## 为什么做不到：天花板效应

三个预注册的"硬场景"是专门设计来制造失败的——把运行时故障做成必然事件：

- `tight-budget-complete`：硬约束 `max_tokens ≤ 1000`，实测 800 时正文 **0 字**（思考吃光预算）
- `batch-forced-flagship`：用户点名 `glm-5.3` 跑 Batch，必定 `1210`
- `kb-fallback`：该账号向量化实测经常 `embedding_stat=2`

结果是 **v2 在这三个场景上拿了 14/15**——GLM-5.3 配上现行说明书，
连这种刻意设计的死局都能自己走出来（自动降级模型、关思考分段生成、改用 embeddings 自建检索）。

**满分率已经在 92%~97%，n=5 撑不起任何显著提升。** 这不是说明书写得不够好，
而是**在这个执行器 + 这类任务上已经没有可测量的空间**。

## 评测过程中修掉的 3 个评分器 bug（如实记录）

本轮判分我自己的评分器出过三个 bug，**三次修正都让 v2 的分数上升**（0/5 → 2/5 → 4/5）：

1. **判分项在测平台而不是测技能**：`rerank-restore-docs` 原第 4 项"最相关的排在第一"——
   探针确认**接口自己**就把"普通发票支持随时申请"排第一，且与正确文档的 `relevance_score`
   并列 `1.0000000000`。这是平台 rerank 模型的排序质量，不是 Agent 或说明书能左右的。**作废**，
   换成可测脚本行为的判据。
2. **正则只认字面数字**：`tight-budget-complete` 判"是否遵守 `max_tokens ≤ 1000`"用的是正则，
   而脚本写的是 `MAX_TOKENS_PER_REQUEST = 800` 再引用变量 → 5 次全被误判为违反约束。
   改为 **AST 常量解析**（含函数参数、`min()`、简单算术）。
3. **`code_only` 会产出语法非法的代码**：剥函数 docstring 时，如果函数体**只有** docstring，
   剥完剩空 body，`ast.unparse` 出来的 `def f():` 后面没东西——下游再 `ast.parse` 直接失败，
   静默回落到正则。补 `ast.Pass()` 修复。

三次修正方向一致地对 v2 有利，这值得警惕，但每一次都是"**判形式而非判结果**"这一类，
口径与此前 9 次完全一致，且对 v2/v3 对称生效。
累计 **12 个评分器 bug**，其中 9 个把正确行为判成了失败。

## 要真正证明准确率提升，需要什么

现有条件下不可能。可行的路径有三条，都超出本轮范围：

1. **换更弱的执行器**（如 `glm-4.5-air` 或更小的模型）——天花板会降下来，说明书的边际价值才测得出。
2. **把 n 提到 20~30**——在 95% 附近要检出 3~5 个百分点的差异，需要的样本量是当前的 4~6 倍。
3. **换更难的任务分布**——但本轮三个"必然失败"的场景已经证明，
   刻意制造的死局 GLM-5.3 自己就能解开，再加难度会偏离真实使用场景。

## 已经确证的部分（不受本轮影响）

- **v2 相对 v1 省 token**：计费当量 **−14.1%（p = 0.019）**，读入上下文的字符 **−52.8%**，准确率无退步。
- **v2 相对不用说明书**：满分率 **39/40 vs 19/40，Fisher p = 4.0×10⁻⁷**；
  每做对一次的成本 **−55.6%**。

**"优化说明书让它更省 token" 已达成且显著；"让准确率进一步提升" 未达成，本轮如实记录为失败。**
