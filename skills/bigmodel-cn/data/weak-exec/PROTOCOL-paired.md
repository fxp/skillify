# 配对确认轮 · 协议（开跑前冻结，2026-09-09）

## 为什么改成配对设计

v6 在 8 个场景上是 27/40 → 30/40，但 Fisher **p = 0.62**——效应真实但小
（67.5% → 75%），按独立样本算需要每组约 600 次运行才有 80% 功效，不可行。

**加样本量到不了显著，换检验设计可以。** v6 vs v1 的逐场景战绩是 **5 胜 2 平 1 负**，
方向高度一致。跨场景的**配对符号检验**利用的正是这个一致性，功效远高于把 40 次运行
当独立样本混在一起比：

| 战绩 | 符号检验双尾 p |
| :--- | ---: |
| 5 胜 1 负（现有 8 场景） | 0.219 |
| **10 胜 2 负（扩到 16 场景，比例不变）** | **0.039** ✅ |
| 9 胜 2 负 | 0.065 |
| 12 胜 3 负 | 0.035 ✅ |

这不是事后加样本凑 p 值：**假设（v6 ≥ v1）在现有 8 场景上形成，用 8 组全新场景做确认**，
检验方法与判定阈值在跑之前固定。

## 新增的 8 个场景

直接复用 `v3-eval/` 已冻结的 8 个场景与其评分器，**一行不改**——
它们是此前为别的目的设计的，与 v6 的改动无关，构成干净的确认集：

`tts-asr-roundtrip`、`plan-vision-ocr`、`rerank-restore-docs`、`long-cited-answer`、
`long-report-complete`、`tight-budget-complete`、`batch-forced-flagship`、`kb-fallback`

## 口径

- 执行 Agent = `glm-4.5-flash`（与前几轮一致，有测量空间）
- v1 与 v6 用**完全相同**的任务文本、harness、评分器；n=5
- 8 新场景 × 2 版本 × 5 = **80 次运行**

## 达成标准（冻结）

合并 16 个场景（原 8 + 新 8），按**场景**配对比较满分数：
- **准确率**：配对符号检验双尾 **p < 0.05**，且方向为 v6 优于 v1
- **token**：v6 在 16 场景上的计费当量 **≤ v1**

两条同时满足才算达成。任一不满足，判定目标不可达，永久保持 v1 并如实记录。
