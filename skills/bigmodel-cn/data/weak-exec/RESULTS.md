# 弱执行器轮：四个版本的对照，以及一个负面结论（2026-09-09）

## 结论：**优化目标不成立。v1（未优化的原版）是四个版本里最好的。**

执行 Agent = `glm-4.5-flash`（明显弱于 GLM-5.3，且实测未被静默重路由），
8 场景 × n=5 = 40 次/版本，任务文本逐字相同，判分用各场景**原来那份冻结的评分器**。

| 版本 | 满分率 | 平均分 | 计费当量 | 每做对一次 |
| :--- | ---: | ---: | ---: | ---: |
| **v1（原版）** | **27/40** | **0.852** | **117,670** | **174,325** |
| v2（拆分 + 速查表 + 读取纪律） | 22/40 | 0.788 | 103,094（−12.4%） | 187,444（+7.5%） |
| v4（保留速查表，删读取纪律，合并回 chat.md） | 22/40 | 0.815 | 128,972（+9.6%） | 234,494（+34.5%） |

v2 vs v1：Fisher p = 0.36；v4 vs v1：Fisher p = 0.36。
**两个"优化版"在准确率上都不如原版，且每做对一次都更贵。**

## 为什么换弱执行器

前三轮都在 GLM-5.3 上测，满分率 92%~97%，**天花板效应**让 n=5 测不出任何差异。
换到 `glm-4.5-flash`，v1 只有 27/40（67.5%），**终于留出 32.5% 的失败空间**——
这才是能检验"说明书优化有没有用"的条件。空间是有了，但优化版没有吃下去，反而更差。

## 机制：省下来的 token 正是准确率所依赖的上下文

| | 每次运行 Read 读入 | chat.md 读入 | tools.md | models.md |
| :--- | ---: | ---: | ---: | ---: |
| v1 | 42,266 | 12,599（100% 必读） | 4,595 | 2,581 |
| v2 | 33,795 | 5,566（拆分后只剩核心） | 3,453 | 1,537 |

v2 拆出去的 `chat-advanced.md` 只有 **45%** 的运行会去读，而 v1 里这些内容本来就在必读的
`chat.md` 里。**强执行器自己知道该读什么，所以不受影响；弱执行器不行。**

v4 按这个机制做了针对性修正（删掉劝阻通读的「读取纪律」、把 `chat.md` 合并回去），
读入量确实回来了（wire +23.3%），**但准确率没回来**——说明问题不只是"读得少"。
剩下的嫌疑是**速查表本身**：v2 和 v4 都含它，都是 22/40；v1 不含，是 27/40。
一大块"这里有 20 个坑"的密集清单，可能在弱模型上挤占了它本该用来读真正接口文档的注意力。
这条没有进一步验证——四轮下来证据方向一致，继续调下去就是在数据上挑结果了。

## 四轮汇总：目标的两半各自的真实状态

| 轮次 | 执行器 | 对比 | token | 准确率 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | GLM-5.3 | v2 vs v1 | **−14.1%（p=0.019）** ✅ | 39/40 vs 38/40（p=1.0）**无变化** |
| 2 | GLM-5.3 | v3 vs v2 | +3.9% ❌ | 35/40 vs 37/40（p=0.71）**无提升** |
| 3 | glm-4.5-flash | v2 vs v1 | −12.4%（p=0.11） | 22/40 vs 27/40 **更差** |
| 4 | glm-4.5-flash | v4 vs v1 | +9.6% ❌ | 22/40 vs 27/40 **更差** |

**「省 token」在强执行器上成立且显著；「准确率提升」四轮全部未能证明，
且在有测量空间的弱执行器上，所有优化版都比原版更差。**

## 据此做的处置

**把线上的 `bigmodel-cn` 回退到 v1。** 理由：

- 准确率是这份说明书存在的意义，token 是次要指标；
- 强执行器上 v1 与 v2 打平（38/40 vs 39/40，p=1.0），v2 的 14% 节省买不到任何准确率；
- 弱执行器上 v1 明显更好（27/40 vs 22/40），且**每做对一次更便宜**（174,325 vs 187,444）；
- 综合两个执行器，v1 是唯一没有在任何条件下变差的版本。

v2 / v3 / v4 全部保留在 `bigmodel-cn-v2-archive/`、`bigmodel-cn-v3/`、`bigmodel-cn-v4/`，
连同各自的运行记录，供后续复查或换条件重测。

## 这轮真正的产出

不是一份更好的说明书，而是一条可复用的经验：

> **拆分 reference、加"只读你需要的那节"这类读取纪律，是在用准确率换 token。
> 换得划不划算取决于执行器强弱——强模型知道该读什么，省下的是冗余；
> 弱模型不知道，省下的是它写对代码所必需的上下文。**

如果要在弱模型上省 token，正确方向不是让它少读，而是**把决策性事实前置到它必读的那一份文件里，
同时不削减参考资料的完整性**——v4 试了前半段（速查表前置）但同时保留了速查表带来的干扰，
下一次该测的是"只前置、不加清单式速查表"这个更小的改动。

# 第五次尝试：v5（照抄式代码片段）——同样失败，且我自己写错了 API

## 与前四轮的区别

诊断 v1 在弱执行器上的 13 次失败后发现：**知识 v1 里全都写了**，弱模型就是找不到、
或找到了也写不对。所以 v5 不再加散文式规则，改成针对 5 个失败簇各给一段**可直接照抄的完整代码**，
references 结构与 v1 逐字相同（已 diff 验证）。

## 结果：两条标准都不满足

| 版本 | 满分率 | **平均分** | 计费当量 | 每做对一次 |
| :--- | ---: | ---: | ---: | ---: |
| **v1（原版）** | **27/40** | 0.852 | **117,670** | **174,325** |
| v2 | 22/40 | 0.788 | 103,094 | 187,444 |
| v4 | 22/40 | 0.815 | 128,972 | 234,494 |
| v5 | 26/40 | **0.885** | 120,482（+2.4%） | 185,358（+6.3%） |

v5 vs v1：Fisher p = 1.00，Mann-Whitney p = 0.84。
**v5 的平均分是四版最高，但满分率仍低于 v1，且 token 没省下来。**

逐场景看，v5 在 4 个场景上追平或超过 v1（`rag-index-embeddings` 3→4、
`async-model-pinning` 4→5、`kb-id-validation` 4→5、`cited-web-answer` 持平 3），
**唯独 `pdf-reuse-fileid` 从 2/5 崩到 0/5**——正是我写了代码片段的那个场景。

## 崩在哪：我的片段教了错误的 API 用法

5 次运行全部照抄了片段里的写法，5 次全部抽不出合同编号。对真实 API 验证后确认**两处都错**：

| 写法 | 实测 |
| :--- | :--- |
| `glm-5.3-flash` + `{"type":"file","file":{"file_id":…}}` | ✅ 正确返回 `HT-2026-0917-XJ` |
| `glm-4.6` + `{"type":"file","file_id":…}`（**我片段里的写法**） | ❌ `1210 messages.content.type 参数非法，取值范围 ['text']` |

1. **嵌套错了**：`file_id` 要放在 `file` 键下面，不是 block 顶层。
2. **模型选错了**：`file` 类型是**视觉模型**的能力（`glm-5.3-flash`/`glm-4.6v`/`glm-5v-turbo` 等），
   `glm-4.6` 根本不支持。

**而 v1 的 `references/chat.md` 第 39 行把这两点都写对了**——包括嵌套结构、三选一的
`file_id`/`file_url`/`file_data`、以及哪些模型支持。我当初该照抄它，却自己凭印象编了一段。

线上的 `bigmodel-cn` 是 v1，没有受影响；v5 从未上线。

## 五轮汇总：目标的两半

| 轮次 | 执行器 | 对比 | token | 准确率 |
| :-: | :--- | :--- | :--- | :--- |
| 1 | GLM-5.3 | v2 vs v1 | **−14.1%（p=0.019）** ✅ | 39/40 vs 38/40 **无变化** |
| 2 | GLM-5.3 | v3 vs v2 | +3.9% ❌ | 35/40 vs 37/40 **无提升** |
| 3 | glm-4.5-flash | v2 vs v1 | −12.4% | 22/40 vs 27/40 **更差** |
| 4 | glm-4.5-flash | v4 vs v1 | +9.6% ❌ | 22/40 vs 27/40 **更差** |
| 5 | glm-4.5-flash | v5 vs v1 | +2.4% ❌ | 26/40 vs 27/40 **未超过** |

**「省 token」只在强执行器上成立且显著；「准确率提升」五轮全部未能证明。**
按预注册标准，本次优化目标**判定为未达成**，线上保持 v1，停止迭代。

## 五轮换来的三条经验

1. **拆分 reference + 劝阻通读 = 用准确率换 token。** 强模型知道该读什么，省下的是冗余；
   弱模型不知道，省下的是它写对代码所必需的上下文。
2. **清单式"陷阱速查表"在弱模型上是负担。** v2/v4 都含它、都是 22/40；v1 不含、27/40。
   一大块"这里有 20 个坑"会挤占它读真正接口文档的注意力。
3. **手写代码片段风险极高。** 片段一旦写错，弱模型会 100% 照抄——v5 的 `pdf` 场景
   从 2/5 直接崩到 0/5。**要放片段，必须逐段对真实 API 跑通再入库**，
   而不是凭对文档的印象手写。这一条比前两条更重要，因为它的失败是静默且系统性的。

# 第六次尝试 v6 与配对确认轮：效应没有复现，目标判定为不可达

## v6 是什么

诊断 v1 的 13 次失败后，针对 5 个失败簇各给一段**可直接照抄的代码**，
**每段都先对真实 API 跑通验证**（这是 v5 缺的那道工序），references 与 v1 逐字相同，
不拆分、不加清单式速查表。SKILL.md 12,827 → 16,218 字节。

## 第一次测量（原 8 场景）：看起来成功了

| | v1 | v6 |
| :--- | ---: | ---: |
| 满分率 | 27/40 | **30/40** |
| 计费当量 | 117,670 | **106,125（−9.8%）** |
| 每做对一次 | 174,325 | **141,499（−18.8%）** |

**但 Fisher p = 0.62，不显著。** 效应真实但小（67.5%→75%），按独立样本算需每组约 600 次。

## 配对确认轮：效应没有复现

加样本到不了显著，于是换**配对符号检验**——利用 v6 在 8 个场景上「4 胜 3 平 1 负」的方向一致性。
用 8 组**全新场景**（复用 `v3-eval/` 已冻结的场景与评分器，一行未改，与 v6 的改动无关）做确认，
检验方法与阈值跑前冻结于 `PROTOCOL-paired.md`。

| 组 | v6 战绩 |
| :--- | :--- |
| 原 8 场景（形成假设的那组） | **4 胜 3 平 1 负** |
| **新 8 场景（确认组）** | **2 胜 4 平 2 负** |
| 合并 16 场景 | **6 胜 7 平 3 负** |

**配对符号检验双尾 p = 0.5078。**

**确认组把效应打没了。** 原来那组 4 胜 1 负是噪声——这正是预注册确认集要防的事，它防住了。

token 也一样缩水：16 场景合并计费当量 **−2.5%**（原 8 场景是 −9.8%），
而线上 token 反而 **+3.4%**。

## 对照冻结标准

| 标准 | 结果 |
| :--- | :--- |
| 准确率：配对符号检验 p < 0.05 | p = 0.5078 → ❌ |
| token：v6 计费当量 ≤ v1 | 113,166 vs 116,124 → ✅ |

**两条未同时满足 → 未达成。**

## 处置：回退到 v1

v6 在强执行器上无退步（39/40 vs 38/40）、在 16 场景上略优（50/80 vs 47/80）、
计费当量略省（−2.5%）——但**没有一项达到统计显著**，而线上 token 还涨了 3.4%。
**收益无法证明的改动不该上线**，回退到 v1。

## 六轮总账

| 轮次 | 执行器 | 对比 | token | 准确率 |
| :-: | :--- | :--- | :--- | :--- |
| 1 | GLM-5.3 | v2 vs v1 | −14.1%（p=0.019）✅ | 39/40 vs 38/40 无变化 |
| 2 | GLM-5.3 | v3 vs v2 | +3.9% ❌ | 35/40 vs 37/40 无提升 |
| 3 | glm-4.5-flash | v2 vs v1 | −12.4% | 22/40 vs 27/40 更差 |
| 4 | glm-4.5-flash | v4 vs v1 | +9.6% ❌ | 22/40 vs 27/40 更差 |
| 5 | glm-4.5-flash | v5 vs v1 | +2.4% ❌ | 26/40 vs 27/40 未超过 |
| 6 | glm-4.5-flash | v6 vs v1（16 场景配对） | −2.5% ✅ | **p = 0.51，效应未复现** |

约 **520 次判分运行、两个执行器、一组预注册确认集**。
**「省 token」只在强执行器 + 特定版本上短暂成立；「准确率提升」六轮全部未能证明。**

## 最终判定

**这份说明书已经在它的局部最优点上。** 我尝试过的每一类改动——
拆分 reference、加陷阱速查表、删读取纪律、加运行时补救、加照抄式代码片段——
要么用准确率换 token，要么两头都不讨好。**目标「省 token 且准确率提升」在现有条件下不可达。**

线上永久保持 v1。v2–v6 连同全部运行记录保留在 `bigmodel-cn-v*-archive/`，供换条件复测。

## 六轮换来的四条经验

1. **拆分 reference + 劝阻通读 = 用准确率换 token。** 强模型知道该读什么，省的是冗余；
   弱模型不知道，省的是它写对代码所必需的上下文。
2. **清单式陷阱速查表在弱模型上是负担。** v2/v4 都含它、都 22/40；v1 不含、27/40。
3. **手写代码片段必须先对真实 API 跑通。** v5 那段写错的文件引用被 100% 照抄，
   该场景从 2/5 直接崩到 0/5。
4. **小效应必须用预注册确认集验证。** v6 在形成假设的那组是 4 胜 1 负，
   在全新确认组只有 2 胜 2 负——**没有确认集，我会把噪声当成果发布出去。**
