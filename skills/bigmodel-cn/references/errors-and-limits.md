# 错误码、速率限制与重试策略

来源：`docs.bigmodel.cn/cn/api/api-code`、`docs.bigmodel.cn/cn/api/rate-limit`

## 响应结构

调用出错时，HTTP 状态码是外层信号，响应体里的业务错误码（`error.code`）才是具体原因：

```json
{"error":{"code":"1001","message":"Header 中未收到 Authentication 参数，无法进行身份验证"}}
```

> 流式（SSE）调用如果在推理过程中异常终止，**不会**返回上面这种错误体，而是在最后一个 chunk 的 `finish_reason` 字段里说明异常原因（比如内容安全拦截、超长截断等）。写流式消费代码时，必须检查 `finish_reason`，不能只判断有没有抛异常。

## 常见业务错误码

| 业务错误码 | HTTP | 含义 | 处理建议 |
| :--- | :--- | :--- | :--- |
| 1000/1001/1003 | 401 | 鉴权失败 / 缺少 Authorization 头 / Token 过期 | 检查 `Authorization: Bearer <API_KEY>` 是否正确携带、Key 是否有效 |
| 1005 | 401 | 账户开启了二次认证，需要二次登录 | 提示用户去控制台完成二次认证 |
| 1113 | 429 | 账户欠费 | 提示用户充值 |
| 1210 | 400 | 请求参数有误 | 检查参数名/类型是否符合本技能包各参考文档里的字段定义 |
| 1211 | 400 | 模型不存在 | 检查 `model` 字段拼写，参考 `references/models.md` |
| 1212 | 400 | 当前模型不支持该调用方式 | 例如给不支持工具调用的模型传了 `tools` |
| 1213 | 400 | 缺少必填参数 `${field}` | 补全参数 |
| 1214 | 400 | `${field}` 参数非法 | 检查取值范围/枚举值 |
| 1215 | 400 | 两个字段不能同时设置 | 常见于 `temperature` 与 `top_p` 同时精细调整、或互斥的输出格式参数 |
| 1220 | 403 | 无权访问该 API | 检查 API Key 所属项目/权限,或该能力是否需要额外申请 |
| 1221/1222 | 400 | API 已下线 / API 不存在 | 检查 endpoint 路径拼写和版本 |
| 1261 | 400 | Prompt 超长 | 缩短输入或改用更大上下文窗口的模型 |
| 1301 | 400 | 输入或生成内容触发内容安全策略 | 调整 prompt，避免敏感内容；必要时接入 `references/tools.md` 里的内容安全审核接口做预检测 |
| 1302 | 429 | 触发账户速率限制 | 见下方"速率限制"一节 |
| 1305 | 429 | 平台服务过载 | 退避重试 |
| 1308/1310 | 429 | 达到用量/次数上限，`next_flush_time` 给出重置时间 | 按重置时间调整调用节奏，或申请提升权益等级 |

完整错误码表见源文档，此处只列出 Agent 在写调用代码和错误处理逻辑时最需要感知的部分。

## 速率限制（Rate Limit）

- 限制维度是**并发请求数**（同一时刻处理中的请求数），按「用户权益等级 × 模型」独立设置上限,不是简单的 QPS。
- 不同模型类别（通用对话模型 / 图像视频生成模型 / 向量模型 / 实时音视频模型）各有独立并发池。
- 具体额度需登录控制台查看：`https://bigmodel.cn/usercenter/proj-mgmt/rate-limits`，无法通过 API 查询,所以代码里不要假设固定的 QPS 数字。
- 触发限流时返回错误码 **1302**（账户级限流）或 **1305**（平台级过载）。

### 给 Agent 的实现建议

1. **必须实现重试与退避**：对 429（1302/1305/1308/1310 等）和 500 类错误做指数退避重试，避免固定间隔的高频重试（文档明确指出这会加重限流）。
2. **用并发池/信号量控制并发度**，不要无限制地并发发请求；批量任务优先考虑 `references/files-batch.md` 里的 **Batch API** 或 `references/chat.md` 里的**异步对话补全接口**，它们专为非实时、大批量场景设计，不占用同步并发额度。
3. **区分错误类型再重试**：401/403/400 类错误是配置或参数问题，重试没有意义，应该直接向用户/日志报错；只有 429/500 类才值得退避重试。
4. **流式调用要检查 `finish_reason`**，不要只依赖 try/except 判断调用是否成功。

## 快速自检清单

写完调用代码后，建议按这个顺序自查一遍：

- [ ] `Authorization` 头是否正确设置为 `Bearer <API_KEY>`（不是 `ApiKey` 或裸 Key）
- [ ] `model` 字段是否是 `references/models.md` 里存在的模型代码
- [ ] 是否给所有可能失败的调用加了错误处理（区分 4xx 配置错误 vs 429/5xx 重试）
- [ ] 是否对高并发/批量场景选择了异步接口或 Batch API,而不是同步接口硬扛
- [ ] 流式场景是否正确解析了 SSE 的 `data: [DONE]` 结束标记和 `finish_reason`
