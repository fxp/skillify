# 第三步：真实 API 验证与修正

核心认知：官方文档和 OpenAPI 规范经常是错的、过时的、或自相矛盾的。只读文档写出来的 skill 看起来很权威，但会把这些错误原样继承，而且没人知道错在哪——直到有人真拿这份 skill 写代码调用真实 API。**判断 skill 质量的标准，是"和真实接口行为对不对得上"。**

## 测什么、按什么顺序

1. **第 2 步留下的所有 `⚠` 标记**（文档未说明 / 自相矛盾）——这是优先清单。
2. **SKILL.md 开头"先确认的几件事"**：Base URL、鉴权 header、最易选错的字段。这几条错了全盘皆错，先用最便宜的只读接口打通。
3. **每类关键结论各测一次**，低成本先行（文本对话、embedding、小文件上传、只读查询），大消耗的（视频生成、大批量任务、创建付费资源）用最小规模，或跳过并显式标注"未验证"。
4. 四类最值得测的地方：
   - 规范标 `required` 的字段，**省略它会不会真报错**。见过同一个字段名在两个入口的必填程度完全不同，规范自己前后矛盾。
   - 文档说响应会带的字段，**默认情况下到底在不在**。见过要显式传某个开关参数字段才出现，文档没提这个前提。
   - 参数值和文档不一致时，**是报错还是静默失效**。静默失效最危险：`tool_choice` 强制指定被当成 `auto`、`response_format: json_schema` 被完全忽略，都是不报错但结果全错。
   - **平台独有、其他家没有对应物的能力**（把文件直接传进对话消息、批处理专属的模型白名单）。这些是文档最语焉不详、Agent 最容易套别家经验编错的地方。
5. 同一个能力如果有多个入口（同步 / 异步、REST / SDK），至少各测一次，别假设行为一致。

## 发现不一致后怎么写回去

每发现一处真实结果和文档不一致，立刻改对应的 reference 文件，写法固定：

```markdown
**已用真实 API 验证（2026-09）**：传 `thinking: {"type": "disabled"}` 到 glm-5.3 会直接报错
`{"error":{"code":"1210","message":"..."}}`，该模型强制开启思考，只能用 `reasoning_effort` 调强度。
```

三个要素缺一不可：**验证日期**、**做了什么**、**原始报错 / 响应片段**。"已验证"三个字没有证据等于没说；带了证据，后人才能判断这条结论是否可能已过期、以及怎么复现。

**文档本身写错的发现要区别对待**。"baseline Agent 猜错了"和"官方文档自己就是错的"不是一回事：后者靠再仔细读文档也抓不到，只有真实调用能暴露，价值最高。这类发现：

- 在 reference 里标明"官方文档示例写错"，并说明文档写的是什么、实际是什么；
- **同时升到 SKILL.md 的"跨领域通用规则"**，因为那一层永远加载，Agent 不读到对应 reference 也能看到；
- 在第 4 步的 `comparison-report.md` 末尾单列一张"评测中修正的文档条目"表。

AutoDL 的例子：文档给 `GET .../instance/pro/snapshot` 画的是"请求 Body 示例"，实测 JSON body 报 `RequestParameterIsWrong`，必须走 query string。这条写进了 SKILL.md 通用规则第一条，并推广成"所有 GET 接口都先假设要 query string"。

## 没有 key、或 key 权限不够时

不要跳过这一步、也不要假装做了。降级方案：

- **分区标注**。SKILL.md 顶部加"验证状态"一节，写清哪些已验证（日期、花费）、哪些仍是文档转录。AutoDL 案例：容器实例 API 全流程真实跑通（花了约 0.03 元），弹性部署 API 因账号无企业认证未验证，SKILL.md 第一节就是这句话。
- **把验证计划写成文件**留给有 key 的人：`<workspace>/verification-plan.md`，按优先级列出要测的结论、用哪个 endpoint、预期成本、怎么判定。第 2 步的 `⚠` 清单直接转过来。
- **第 4 步按用户要的范围降级**。用户只要"草稿"时，第 4 步交付 `evals/evals.json`（场景 + 断言写好）和验证计划，不跑对照、不写 `comparison-report.md`，在 SKILL.md 验证状态一节写明"对照实验待真实 key 到位后进行"。用户要"证明有用"但没 key 时，跑"文档保真度对照"：with / without skill 的代码对照官方文档判对错，报告里必须写明这是文档保真度而非真实调用打分，两者可信度不同。
- **所有报错字符串都标来源**。没 key 的草稿里出现的 `400 ...`、错误码、"会被拒绝"，全部是文档转录，要在文件头和出现处标"文档原文，未实测"——子 Agent 和你自己都很容易把它们写得像实测结论。
- 权限类报错本身就是发现：`{"code":"TORealName","msg":"未完成实名认证"}` 这种应该作为"写创建类代码前先确认账号状态"的规则写进 SKILL.md，而不是当成验证失败略过。

## 每次改动后重验

哪怕只是小改一个 reference 文件，也要重新跑受影响的验证。改动附近的内容很容易把之前验证过的结论改坏（字段名顺手"修正"回文档的错误写法），不要假设之前的验证仍然成立。

## 卫生

- **Key 只作为环境变量传给命令本身**，不写进任何文件。验证结束后全仓库 `grep -rn "<key 的前 8 位>"` 一遍，再继续下一步。
- 测试产生的资源（上传的文件、临时知识库、跑起来的 Batch 任务、创建的实例）用完立即清理，不在用户账号里留垃圾；实例类资源要确认已释放，不然会持续计费。
- 在 workspace 里记一份 `verification-log.md`：日期、endpoint、请求要点、结果、花费。第 4 步写报告时直接引用。
