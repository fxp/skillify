# 第二步：结构化撰写

目标：把"一堆文档页面"重组成 Agent 能高效导航、按需查阅的 skill，而不是把文档结构原样照搬。

**先加载 `/anthropic-skills:skill-creator`**，按它的规范初始化目录（frontmatter 只允许 `name` / `description` / `license` / `allowed-tools` / `metadata` / `compatibility`，`name` 用 kebab-case，SKILL.md 控制在几百行内），再往里填内容。不要先凭印象搭结构、最后再去凑校验。

## 三层渐进加载

```
<platform-skill>/
├── SKILL.md                    # 永远整份加载：路由表 + 跨领域通用规则，不放字段细节
├── references/
│   ├── models.md               # （如适用）模型 / 资源 / 规格目录与选型建议
│   ├── <domain-a>.md           # 按"开发者想做什么"分组，不按文档页面分组
│   ├── <domain-b>.md
│   └── errors-and-limits.md    # 错误码、速率限制、重试策略
└── evals/
    └── evals.json              # 第 4 步的对照场景（打包时自动排除）
```

**分组原则**：按开发者的真实意图分（"对话补全"一个文件、"图像视频生成"一个文件），不照抄文档站目录树。官方文档常把关系很近的东西拆得很散——同一个"文档解析"能力分散在三个入口（塞进对话消息、专门的异步解析服务、独立的 OCR 接口），一份好的 skill 应该在一个地方把这些选项摆在一起做对比，帮 Agent 做选型，而不是逐页照搬。

每个 reference 文件的目标区间大约 150-800 行。超过 800 行且明显混了两个能力域就拆；超过 300 行的文件开头加一个目录。

## SKILL.md 骨架

```markdown
---
name: <platform>
description: 接入 <平台全名>（<域名>）的 API 使用手册——涵盖 <能力域 1、2、3…>。当用户提到"<产品名>""<域名>""<SDK 包名>""<常见别称>"，或要求写代码调用上述任意能力时，应主动使用本技能，不要凭记忆编造接口参数或误用 <相似平台> 的接口习惯。
---

# <平台> 接入指南

一段话：平台是什么、API 覆盖哪几块、本 skill 的目标（第一次就跑通）。

## ⚠ 验证状态（有未验证区域时必须有这一节）
哪些 endpoint 已用真实 key 验证（日期、花费），哪些仍是文档转录。

## 用之前先确认 N 件事
1. Base URL 固定为 …
2. 鉴权精确格式：请求头 `…`（和多数平台不同之处要点名）
3. 最容易选错的那个字段（模型名 / 区域 / 规格 ID…）去哪核对

## 30 秒跑通第一个请求
最便宜的一个 endpoint，curl + 目标语言各一份。

## 能力域导航
| 我想做什么 | 参考文件 | 涉及的核心 endpoint |
| … | `references/x.md` | `POST /…`、`GET /…` |

## 跨领域的通用规则（写代码前必读）
同步 / 异步怎么选、流式协议怎么消费、响应统一结构、金额 / 时间单位、
两套 API 之间不能混用的标识、以及第 3 步发现的所有"文档本身写错"的条目。

## 目录结构
文件树 + 一句"内容整理自 <docs URL>（抓取于 YYYY-MM），实际调用报错优先信任 API"。
```

导航表是 SKILL.md 的核心：Agent 拿到任务后看一眼表就知道读哪个文件，不需要通读全部。

## reference 文件里每个 endpoint 的统一格式

```markdown
### <功能名>
**Endpoint**: `METHOD /path`
**用途**: 一两句话，和相邻 endpoint 的区别

**关键参数**
| 参数 | 类型 | 必填 | 默认值 | 说明 |
只列真正重要的，不把 schema 每个字段都抄一遍；枚举值写全；互斥关系写在说明里。

**示例请求**
curl 一份 + 目标语言一份（用环境变量读 key）。

**示例响应**
关键字段，可精简，但字段名和嵌套层级必须和规范 / 实测一致。

**注意事项**
踩坑点、和其他参数的互斥、限制、`⚠ 文档未说明` 的地方。
```

统一格式的意义是让 Agent 读每个 endpoint 时有稳定预期，扫一眼就能定位到参数表。

## 并行委派给子 Agent

一个平台常有几十个 endpoint、6-10 个能力域，一个人顺序写效率低，且越到后面越敷衍。做法：

1. 按能力域把 endpoint 分成 4-6 组，每组对应 `openapi-summary/<tag>.md` + 相关的 `pages/*.md` 路径。
2. **一次性并行**派出所有子 Agent（各组互相独立，没有先后依赖）。碰到并发上限派不出去的组，自己顺序写，不要反复重试。
3. 自己写 SKILL.md 和需要全局视野的文件（`models.md` 这类"该选哪个"的文件）。
4. 收回后通读一遍：格式是否统一、有没有编造、跨文件引用的路径对不对、同一张附录表（区域代码、镜像 ID）是否只维护一份。

**不要和子 Agent 抢同一个文件**。实际跑过的 4 次委派里有 3 次出现父 Agent 与子 Agent、或两个子 Agent 互相覆盖同一路径：父 Agent 看到文件"还没出现"就自己写了一版，随后子 Agent 完成时又把它覆盖掉，或反过来。规则：

- 分配给子 Agent 的路径，在收到它的完成通知之前不要自己写；等待期间做别的（SKILL.md、models.md、evals）。
- 要求子 Agent 写完后在同目录留一个 `<file>.done`（一行：行数 + ⚠ 数），父 Agent 用它判断完成，不依赖通知是否及时。
- 真要接管（子 Agent 明确失败或超时很久），先 `ls -l` 看该路径的修改时间，再决定是补写还是合并，不要盲目覆盖。

给每个子 Agent 的 prompt 模板：

```
你在为 <平台> 写 Claude Skill 的一个 reference 文件：references/<domain>.md。

输入材料（只能依据这些，不要用你自己对这个平台的记忆）：
- OpenAPI 摘要：<scratch>/openapi-summary/<tag>.md
- 文档源页：<scratch>/pages/<a>.md, <b>.md, …
- 鉴权与 Base URL：<scratch>/auth.md

写作规范：
- Base URL：<…>；鉴权 header：<精确格式>；示例代码用环境变量 <ENV_NAME> 读 key。
- 每个 endpoint 用这个格式：<粘贴上面的 endpoint 模板>
- 示例语言：curl + <目标语言>。
- 不要编造输入材料里没有的字段、枚举值、默认值。材料没写清楚的地方标 `⚠ 文档未说明`，不要猜。
- 规范和 Markdown 页面矛盾时两边都写出来，标 `⚠ 文档自相矛盾`，留给真实调用去判。
- 报错信息、错误码、"会返回 400"这类行为描述，如果来自文档而不是实测，一律写成"文档原文，未实测"，不要写成好像你调用过。
- 写完后在同目录写 `<domain>.md.done`（一行：行数 + ⚠ 数量）。
- 按开发者意图组织小节（"我想 X"），相近能力放一起对比，不按页面顺序。
- 目标 <N>-<M> 行。文件开头放一个目录。
- 写完后列出你标了 ⚠ 的所有位置，作为回复的最后一段。
```

`⚠` 标记很重要：第 3 步验证时，这些就是优先测试清单。
