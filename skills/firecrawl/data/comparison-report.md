# firecrawl skill — 对照实验报告

5 个场景，每个场景两个独立子 Agent：一个先读 `SKILL.md` + 对应 reference 文件再答题，一个完全不给任何提示、只凭通用知识答题。评分依据是 `evals/evals.json` 里预先写好的 expectations 清单（全部来自本轮对 Firecrawl 真实 API 的实测发现，不是凭空编的"应该怎样"）。

## 总览

| # | 场景 | 有 skill | 无 skill | 结论 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | JSON 格式必须带 `schema`，裸字符串会静默失败 | 5/5 | 0/5 | **完胜** |
| 2 | crawl 是异步任务，POST 只给 job id 不给内容 | 5/5 | 3/5（走 SDK 封装绕过了坑） | **优势明显，非碾压** |
| 3 | `/extract` 已废弃，该用 `/scrape` JSON 格式 | 5/5 | 0/5 | **完胜** |
| 4 | `map` 只覆盖给定路径，不会自动扩展到全站 | 5/5 | 3/5（大方向猜对，具体做法猜错） | **优势明显，非碾压** |
| 5 | `search` 默认会抓每条结果的正文，不是纯摘要 | 5/5 | 0/5，且给出了错误的成本估算 | **完胜** |

3 个场景（1、3、5）是干净的完胜，2 个场景（2、4）无 skill 版本凭合理的通用工程直觉蒙对了大方向，但在细节上仍然出错或缺了验证依据——如实报告，不夸大成"5 战全胜"。

---

### 场景 1：JSON 格式必须带 `schema` — 完胜

**Task**：抓 example.com，只要页面标题的结构化 JSON。
**Why 选它**：`formats: ["json"]`（裸字符串）是最符合直觉的第一次尝试，因为其它格式（`markdown`/`html`/`links`…）确实都能这么传；只有 `json` 和 `changeTracking` 需要对象形式。这是本轮验证里发现的头号静默失败陷阱。

- **有 skill**：正确用 `formats: [{"type":"json","schema":{...}}]`，代码里显式检查 `data["json"] is not None` 才认定成功，注释直接点出"裸字符串会静默失败"。
- **无 skill**：用的是 `https://api.firecrawl.dev/v1/scrape`（旧版本）+ `"formats": ["json"]`（裸字符串）+ 独立的顶层 `jsonOptions` 字段——这正是 v1 时代的写法，如果真的按 v2 语义跑，会精确踩进验证到的那个陷阱：`success:true`、`data.json` 为 `null`、真实失败信号藏在 `data.warning` 里，代码完全没有处理这种情况。

### 场景 2：crawl 是异步任务 — 优势明显，非碾压

**Task**：爬一个文档站的前 20 页，收集每页 markdown。
**Why 选它**：`POST /crawl` 只返回 job id、不含任何页面内容，是本轮验证里最容易踩的"用同步 API 的直觉去用异步接口"陷阱。

- **有 skill**：手写 REST 调用，明确提交→轮询 `GET /crawl/{id}` 直到 terminal state→从轮询响应的 `data` 字段取内容→处理 `next` 分页，还补充了"`completed==total` 不代表没有失败页，需要另查 `/errors`"这类验证时发现的细节。
- **无 skill**：用了官方 SDK 的 `crawl_url()` 方法并显式传了 `poll_interval` 参数，靠"SDK 内部会做轮询"这个假设绕开了这个坑——如果 SDK 真的按文档承诺的那样封装了轮询逻辑，这条路径本身是对的，只是没有验证过、也没有处理分页和错误页两个细节。**这不是一次干净的胜利**：无 skill 版本靠"用官方 SDK 而不是裸调 REST"这个合理的工程直觉，侥幸避开了最核心的坑，但仍然比有 skill 版本粗糙。

### 场景 3：`/extract` 已废弃 — 完胜

**Task**：从 3 个已知 URL 分别抽取价格和产品名，"用专门做结构化抽取的端点"。
**Why 选它**：题目原话就是在引导选择"专门的端点"，而 `/extract` 无论是名字还是文档定位都最符合这个描述——恰恰是它已经被运行时标记废弃，文档页自己又推荐了另一个不同的替代方案（`/agent`），两个说法互相矛盾。

- **有 skill**：主动放弃 `/extract`，用 `/scrape` 的 JSON 格式对 3 个 URL 分别调用，并解释了不用 `/extract` 的具体原因（运行时废弃警告 + 约 4 倍的 credits 成本）。
- **无 skill**：完全没有意识到 `/extract` 已被标记废弃，把它当作首选方案介绍，用 `FirecrawlApp.extract()` 实现，通篇没有出现任何一句关于弃用的提示。这是本轮 5 个场景里区分度最干净的一个。

### 场景 4：`map` 只覆盖给定路径 — 优势明显，非碾压

**Task**：想知道一个文档站子路径下"整站"有哪些页面，不要漏掉别的路径下的文档。
**Why 选它**：`map` 名字暗示"画出整个网站的地图"，但实测传一个具体子路径时只返回这个路径下发现的链接。

- **有 skill**：直接点出这个反直觉行为（附真实 `warning` 字段原文），策略是 map 子域名根路径、覆盖不足再兜底 map 顶级域名，并且明确提醒"`search` 参数只是按相关性重排序，不是过滤器，别指望靠换关键词补全结果"。
- **无 skill**：也猜对了"应该用根域名而不是子路径"这个大方向（属于合理的通用工程直觉，不算意外），但接着给出了一个不成立的补救策略——用 `"docs"`/`"api"`/`"reference"` 等关键词反复调用 `search` 参数"弥补单次链接图遍历可能漏掉的深层页面"，这正好是有 skill 版本明确警告过的误用（`search` 不是覆盖率增强开关）。也没有检查或提及 `warning` 字段。**大方向对，具体手段错**，且完全没有真实验证依据支撑。

### 场景 5：`search` 默认抓正文 — 完胜，且无 skill 版本给出了错误的成本估算

**Task**：搜索一个关键词，只要前 5 条的标题链接，强调要控成本。
**Why 选它**：`search` 这个名字暗示"和普通搜索引擎一样只给摘要"，但实测每条结果默认会带完整抓取的 markdown 正文（`scrapeOptions.formats` 默认就是 `['markdown']`）。

- **有 skill**：正确解释了默认行为，尝试用 `scrapeOptions:{"formats":[]}` + `highlights:false` 关闭正文抓取，代码里加了一段自检逻辑核实是否真的生效（因为这个关闭手法没有被实测验证过），给出了双轨成本估算（生效约 2 credits，不生效约 7 credits）。
- **无 skill**：明确断言"只要不传 `scrapeOptions` 参数，就只返回标题/链接/摘要，不会抓取正文"——这个结论和实测结果直接相反（不传任何参数时同样会抓正文），并且在此错误前提上给出了"约 1 credit、几百字节到几 KB"的成本估算，同样是错的。这是本轮里"无 skill 版本自信地给出一个听起来合理、但被实测证伪的答案"最典型的一次。

## 诚实说明

本报告的"完胜"判定全部基于 expectations 清单逐条核对，不是主观印象；"优势明显，非碾压"的两个场景是因为无 skill 版本靠合理的通用工程直觉（用官方 SDK 处理异步、往根域名而不是子路径 map）蒙对了主干判断，据实记录，不夸大为全胜。所有引用的响应片段和报错文案均来自 `firecrawl-workspace/verification-log.md` 里记录的真实调用，不是转述文档。
