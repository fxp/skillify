# 从开发者文档生成 API 接入 Skill

给一个开放平台/SaaS 的开发者文档站（一个 URL），产出一份结构规范、内容经过真实调用验证、且证明过确实比"不装技能直接凭经验写代码"更好的 Skill。这是本项目（`fxp/skillify`）积累的第一手方法论，来自实际生成 [`skills/bigmodel-cn`](../bigmodel-cn) 的完整过程——那个案例里，光是"读文档"这一步就会把 7 处文档本身的错误原样抄进技能包，必须靠真实调用才能发现。

## 全局流程

```
1. 抓取与勘探  →  2. 结构化撰写  →  3. 真实 API 验证与修正  →  4. 用真实对照实验证明价值  →  5. 打包发布
```

不要跳过第 3、4 步直接交付——第 1、2 步产出的是"看起来权威、实际上继承了官方文档所有错误"的半成品，只有走完真实调用验证，才是真正对得起"Skill"这个名字的东西。

---

## 第一步：抓取与勘探

目标：在写任何一行 Skill 内容之前，先搞清楚这个平台真正的 API 全貌，而不是凭对"这类平台大概长什么样"的印象去写。

1. **先找 `llms.txt`**：很多现代文档站（Mintlify、GitBook 等生成的站点）在根路径提供 `/llms.txt`，是一份给 AI 用的完整页面索引（标题+URL+摘要），比人肉点导航栏快得多。用浏览器/`curl` 直接访问 `https://<docs-domain>/llms.txt` 试一下。
2. **找 OpenAPI / AsyncAPI 规范文件**：文档站通常会暴露 `openapi.json`（REST API）或 `asyncapi.json`（WebSocket/事件类协议），路径常见于 `/openapi/openapi.json`、`/api-reference/openapi.json` 等，`llms.txt` 末尾常会直接列出。**这是全流程里最重要的一份原始材料**——它有精确的字段类型、`required` 列表、枚举值，人类写的 Markdown 教程通常只挑重点讲，OpenAPI 规范才是"完整但没有解释"的那份权威真相。用 Python 把它 parse 出来，对每个关心的 endpoint 递归展开 `$ref`，落地成一份可读的 schema 摘要——不要指望自己通读几千行原始 JSON。
3. **批量下载 Markdown 源页面**：`llms.txt` 里每条链接通常在结尾加 `.md` 就能拿到该页面的纯 Markdown 源码（不用截图/不用渲染 DOM）。用 `xargs -P 8` 并发批量拉取到本地 scratch 目录，比一页页用浏览器打开快一个数量级。
4. **摸清鉴权方式**：从 OpenAPI 的 `securitySchemes` 或文档里明确鉴权头的确切格式（`Authorization: Bearer <key>` / `x-api-key` / 自定义 header 等）——这是几乎每个 endpoint 都要用到的细节，错了全盘皆错，值得在这一步就锁死。

产出：一个本地 scratch 目录，装着原始 Markdown 页面 + 按能力域分组、已展开 `$ref` 的 OpenAPI schema 摘要文本。这些是第二步的输入，不是最终交付物。

## 第二步：结构化撰写

目标：把"一堆文档页面"重组成一份 Agent 能高效导航、按需查阅的 Skill，而不是把文档结构原样照搬。

### 设计 Skill 结构（渐进式加载三层）

```
<skill-name>/
├── SKILL.md              # 永远整份加载：能力域路由表 + 跨领域通用规则，不放具体字段细节
└── references/
    ├── models.md          # （如适用）模型/资源目录、选型建议
    ├── <domain-a>.md       # 按"开发者会问的问题"分组，不是按官方文档的页面分组
    ├── <domain-b>.md
    └── errors-and-limits.md
```

**分组原则**：按开发者的真实意图分组（比如"对话补全"一个文件、"图像视频生成"一个文件），而不是照抄文档站的目录树——官方文档常常把关系很近的内容拆得很散（比如"文档解析"在这家平台就分散在三个不同入口：直接塞进对话消息、走专门的异步解析服务、走独立的 OCR 接口），一份好的 Skill 应该在一个地方把这些选项摆在一起对比，帮 Agent 做选型判断，而不是逐页照搬。

**每个 endpoint 的统一格式**（保证 Agent 读起来有稳定预期）：
```
### 功能名
**Endpoint**: `METHOD /path`
**用途**: 一两句话
**关键参数**（表格：参数名 | 类型 | 必填 | 默认值 | 说明——只列真正重要的，不要把 schema 每个字段都抄一遍）
**示例请求**：curl + 目标语言（如 Python）各一个
**示例响应**：关键字段，可精简
**注意事项**：踩坑点、和其他参数的互斥关系、限制
```

**SKILL.md 正文只做路由**：能力域导航表（"我想做 X → 读哪个 reference 文件 → 涉及哪些 endpoint"）+ 跨领域通用规则（同步异步怎么选、流式协议怎么消费、鉴权、速率限制等所有 reference 文件都会用到的共性知识）。具体字段表、代码示例一律放 reference 文件，SKILL.md 保持在几十到一百多行，参考本仓库 [`skills/bigmodel-cn/SKILL.md`](../bigmodel-cn/SKILL.md) 的写法。

### 并行委派给多个子 Agent 撰写

一个平台常常有几十个 endpoint、覆盖 6-10 个能力域，自己一个人顺序写效率低、容易在后面几个文件上敷衍。做法：

1. 把 endpoint 按能力域分成 4-6 组（每组给一份对应的 OpenAPI schema 摘要文本 + 相关 Markdown 源文件路径）。
2. 给每个子 Agent 一份**统一的写作规范**（Base URL、鉴权格式、上面那个 endpoint 格式模板、"不要编造源文件里没有的字段"的明确要求、目标行数区间）。
3. 一次性并行发出所有子 Agent 任务，而不是一个写完再派下一个——独立的能力域之间没有依赖关系。
4. 自己负责写 SKILL.md 本体和"模型/资源选型"这类需要通读全局才能写好的文件，把体力活（逐个 endpoint 摘抄字段表）分给子 Agent。

## 第三步：真实 API 验证与修正（最容易被跳过、但最重要的一步）

**核心认知**：官方文档和 OpenAPI 规范经常是错的、过时的、或者自相矛盾的。只读文档写出来的 Skill，看起来很权威，但会把这些错误原样继承下去，而且没人知道错在哪——直到有人真的拿这份 Skill 写代码调用真实 API 才会发现。**判断一份 Skill 质量的标准，不是"抄没抄对文档"，是"和真实接口行为对不对得上"。**

如果拿得到真实 API Key（哪怕是免费额度/低成本调用），把 Skill 里写的每一类关键结论都实测一遍：

- 挑选**低成本、能快速出结果**的 endpoint 优先测（文本对话、embedding、小文件上传），大额消耗的（视频生成、大批量任务）视情况酌情测或用最小规模测。
- 对每一处"规范说必填"的字段，实测一下**省略它会不会真的报错**——本项目里发现同一个字段名在两个不同入口的必填程度完全不同，规范文档自己都前后矛盾。
- 对每一处"响应会带某个字段"的描述，实测一下**默认情况下这个字段到底在不在**——发现过好几处"要显式传某个开关参数，这个字段才会出现"，文档没提这个前提条件。
- 特别关注**没有 OpenAI/等类似平台对应能力的独有功能**（比如直接把文件传进对话消息、平台专属的批处理模型白名单）——这些是文档最容易语焉不详、Agent 最容易凭其他平台的经验编错的地方。
- 每发现一处真实调用结果和文档不一致，立刻回去改对应的 reference 文件，并且**标注验证日期**（如"已用真实 API 调用验证，2026-09"），附上实际报错信息原文或响应片段作为证据——这比空口说"已验证"有说服力得多，也方便未来的人判断这条结论是否可能已经过期。
- 用完测试数据/资源（上传的测试文件、临时知识库、跑起来的 Batch 任务等）记得清理，不要在用户账号里留垃圾。
- **绝不把真实 API Key 写进任何会被提交/发布的文件**——测试过程中 Key 只作为环境变量传给命令本身，用完立刻做一次全仓库 `grep` 确认没有 Key 泄漏，再继续下一步。

---

## 第四步：用真实对照实验证明价值

目标：不要只交付"我觉得这份 Skill 应该有用"，要交付"这是实测出来的，有用在哪、体现在哪几个具体场景"。

1. **设计测试场景时，专挑"有经验的开发者会凭其他平台的直觉写错"的任务**，而不是"这个平台的标准 Hello World"——后者预训练知识本来就覆盖得不错，测不出技能包的价值。好的场景来自第三步里发现的那些真实偏差：比如"这个平台不支持某个其他家平台都支持的标准参数，但不会报错，会静默失效"这类坑，最容易在真实调用里现出原形，也最难靠读代码发现。
2. 每个场景都跑两个版本：一个 Agent 读了 Skill 再写代码（with-skill），一个 Agent 完全凭自己的知识写代码（baseline，不给它看 Skill）。同一个 prompt，只有"有没有 Skill"这一个变量。
3. **打分依据真实调用结果，不是凭代码读起来顺不顺眼**——用第三步里实测过的真实报错信息去判定 with/without 两版代码在生产环境里到底会不会跑通，而不是主观判断"这段代码写得像不像对"。
4. **诚实报告，不要为了显得 Skill 有用而夸大**：有些场景两版代码会打平（比如某个冷门细节碰巧在预训练语料里被覆盖到了，或者 baseline 用了足够健壮的防御性编程习惯，意外规避了它自己都不知道的坑），这种"平局"和"技能包获胜"一样值得如实记录——一份诚实的"7 赢 7 平"比夸大的"14 战全胜"更让人相信这份评测是认真做的。
5. 把每一轮测试的 prompt、打分依据、真实调用证据留档（本仓库 `skills/bigmodel-cn/data/` 就是这么做的），不只是给一个"通过率 92%"的数字——数字背后的推理过程才是能让人信任这份评测的东西。

---

## 第五步：打包发布

1. 用 `skill-creator` 技能自带的 `scripts/package_skill.py` 打包，它会自动跑一遍格式校验、排除 `evals/`/临时数据目录。
2. 检查 `SKILL.md` 是否仍在几百行以内、`description` 是否列全了用户可能提到的触发词（产品名、平台域名、SDK 包名、常见别称）。
3. 如果某个 reference 文件明显偏大（比如把好几个关系不算特别紧密的能力域塞进了一个文件），考虑按子领域再拆一次，换取更细粒度的按需加载。

---

## 反面案例：只做第一、二步会得到什么

一份"看起来很完整"、字段表格齐全、代码示例语法都对的 Skill——但其中混着这些真实发生过的错误：一个被规范标记为必填、实际上从不校验的字段；一处响应字段名文档写错、实测完全不存在的位置；一个平台特有的、任何通用知识都猜不到的隐藏限制（比如"某个批处理服务只认一份和主力模型清单完全不重合的老模型白名单"）。这些错误不会在代码审查里被发现——只有真的拿着这份 Skill 写代码、真的调用一次 API，才会暴露。这正是第三、四步存在的意义。
