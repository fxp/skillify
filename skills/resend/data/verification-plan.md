# Resend skill — verification plan

Status: this skill (`../resend/`) was produced from steps 1–2 of the `create-doc-skill` methodology only (fetch real current docs, structure them into `SKILL.md` + `references/`). Step 3 (real API verification) and step 4 (with/without comparison) were **not done** — no Resend API key was available at authoring time (2026-09-21). This file is the priority-ordered list of what to test once a key is available, per `create-doc-skill/references/verify.md`'s "没有 key、或 key 权限不够时" fallback plan.

Cost/risk profile note: Resend's free tier gives 100 emails/day and 3,000/month at zero cost, and every read-only endpoint (list/get) is free regardless of tier. Almost everything below can be verified within the free tier's daily quota. The one thing that costs real setup time (not money) is domain verification — it needs a domain you actually control DNS for. If no such domain is available, use a cheap throwaway domain from a registrar, or skip domain-dependent tests and mark them explicitly unverified.

## Priority 1 — cheap, structural, "does the 30-second example even work"

These gate everything else; if wrong, most of the skill is wrong.

1. **Base send + response shape.** Run the exact SKILL.md "30-second first run" snippet (curl and Python) against `onboarding@resend.dev` → `delivered@resend.dev`. Confirm: `200`/`201` status, response body is exactly `{"id": "<uuid>"}`, no extra fields. **Expected cost: 1 email, well within free quota.**
2. **`User-Agent` 403 trap (SKILL.md item 3).** Send the same request via raw `curl` deliberately *without* a `User-Agent` header. Confirm it actually returns `403` with error code `1010` as documented — this is the single most-repeated claim in the skill and currently rests entirely on one knowledge-base page.
3. **Auth header format.** Confirm `Authorization: Bearer re_xxxxxxxxx` is exact — test a malformed/expired/deleted key and confirm the documented `401 missing_api_key` / `403 restricted_api_key`/`suspended_api_key` error types and messages match exactly (not just "some 401/403").
4. **Node vs Python error-handling divergence (SKILL.md item 5 / eval scenario 3).** This is the highest-value structural claim to confirm, since it's stated as an absolute and drives a whole eval scenario. In Node, trigger a real validation error (e.g. omit `subject`) and confirm the promise resolves to `{ data: null, error: {...} }` rather than throwing. In Python, trigger the same and confirm it raises `resend.exceptions.ValidationError` (or similar) rather than returning an error-shaped dict. Also confirm the Python `ValueError` claim for a missing required field (distinct from `ResendError`) if it's reachable without a real request (may be a client-side check before the HTTP call).

## Priority 2 — the unverified-domain trap (core to the task brief, eval scenario 1)

5. **Unverified domain — exact error.** `POST /emails` with `from` on a domain never added to the account. Confirm `403`, `type: validation_error`, and that the message text matches (or has drifted from) `` The `domain.com` domain is not verified... ``. Confirm there is genuinely **no fallback send** — the email does not appear in the dashboard as sent-from-somewhere-else.
6. **Verified-but-mismatched domain.** Add and verify a real domain as `sending.yourdomain.tld`, then send `from` the bare `yourdomain.tld` (or a different subdomain). Confirm the distinct mismatch-flavored `403 validation_error` and capture its exact message (currently only summarized from `/docs/knowledge-base/403-error-domain-mismatch`, not quoted verbatim like the unverified-domain one is).
7. **`resend.dev` restriction.** Send `from: onboarding@resend.dev` to an address that is *not* the account's own email. Confirm the exact `403 validation_error` message and that it really is scoped to "your own account email" (not, say, any address at your account's already-verified domains).
8. **Full domain verification walkthrough on a real domain.** Add a domain via `POST /domains`, capture the returned `records` array, add them at a real DNS provider, call `POST /domains/{id}/verify`, and confirm: (a) which record scheme you actually get (TXT+MX pair vs CNAME pair — `references/domain-verification.md` claims this depends on when the domain was created, currently unverifiable), (b) the domain-level `status` values actually observed through the lifecycle (`not_started` → `pending` → `verified`, and whether `partially_verified` is real and reachable), (c) whether `GET /domains/{id}` before DNS is added really shows `not_started` as the OpenAPI example implies.

## Priority 3 — batch sending + the attachments spec-vs-docs contradiction (eval scenario 2)

9. **Batch attachments — does the OpenAPI schema's permissiveness or the prose restriction actually govern?** This is the single most concrete, cheaply-testable "doc bug" candidate in this skill. `POST /emails/batch` with 2 items, one of which includes a valid `attachments` array (small base64 content). Confirm whether the request: (a) is rejected outright with a validation error naming `attachments`, (b) succeeds but silently drops the attachment, or (c) actually works despite the prose saying otherwise (i.e. the prose docs are stale and the OpenAPI schema is the current truth). Whichever it is, **update SKILL.md cross-cutting rule 2 and `references/batch-sending.md` with the real behavior and exact error/response**, since right now this skill only has two prose citations against one schema, no observed behavior.
10. **Batch partial-failure behavior.** Send a batch with one item missing a required field (`subject`) and the rest valid. Confirm whether the whole call fails atomically (as `references/batch-sending.md` currently assumes) or whether valid items still send with a per-item error surfaced somehow — and whether the error response identifies which array index failed.
11. **Batch response ordering.** Confirm `data[i]` in the response really does correspond 1:1 in order to request item `i`, across a batch with at least 5 items with visibly different recipients.

## Priority 4 — rate limits, quotas, idempotency (eval scenario 4)

12. **Rate limit is genuinely per-team, not per-key.** Requires two API keys on the same team (easy: create a second key via `POST /api-keys`). Fire concurrent requests from both keys totaling >10/s combined and confirm `429`s occur even though neither key alone exceeded 10/s. This is the single claim eval scenario 4 hinges on and is currently only sourced from one knowledge-base page's prose example, never observed.
13. **Rate limit response headers.** Confirm `ratelimit-limit` / `ratelimit-remaining` / `ratelimit-reset` / `retry-after` are actually present and sensible on both a normal 200 response and a 429.
14. **Daily quota counts multi-recipient sends correctly.** Send one `POST /emails` with 5 addresses in `to` on a free-tier account, then check `x-resend-daily-quota` response header before/after — confirm it incremented by 5, not 1, per the "each recipient counts separately" claim in `references/errors-and-limits.md`.
15. **Idempotency key behavior — all three documented response shapes.** (a) Send the same request+key twice within 24h, confirm the second call returns the same email `id` without sending twice (check the dashboard/inbox count, not just the response). (b) Reuse a key with a *different* payload, confirm `409 invalid_idempotent_request`. (c) Fire two requests with the same key genuinely concurrently, confirm `409 concurrent_idempotent_requests` is reachable (may need to race two HTTP clients).

## Priority 5 — webhooks (eval scenario 5)

16. **Webhook creation requires explicit `events` — confirm no implicit subscription.** Create a webhook with `events: ["email.sent"]` only, then trigger a bounce via `bounced@resend.dev`. Confirm the endpoint receives **no** `email.bounced` event (proving the opt-in claim), then update the webhook to include `email.bounced` and confirm it now arrives.
17. **Suppression happens without any webhook at all.** With zero webhooks configured, send to `bounced@resend.dev` twice. Confirm the second send is auto-suppressed (`email.suppressed`-equivalent behavior visible in the dashboard / a `GET /emails/{id}` showing `suppressed` status) purely from platform-side suppression, proving webhooks are not required for the baseline protection claimed in `domain-verification.md` and SKILL.md rule 3.
18. **Signature verification round-trip.** Stand up a real endpoint (even a temporary one via `ngrok`/Resend CLI's `webhooks listen`), receive a genuine webhook, and confirm `resend.webhooks.verify()` (or the manual Svix path) succeeds on the real raw body/headers and fails when the body is re-serialized from parsed JSON (confirming the "must use raw body" warning is real and not just defensive advice).
19. **The five spec-gap webhook endpoints (`references/webhooks.md`'s "⚠ 文档自相矛盾" table).** Confirm `POST /webhooks/{id}/signing-secret/rotate`, `GET /webhooks/{id}/events`, `GET /webhooks/{id}/events/{event_id}`, `POST /webhooks/{id}/events/{event_id}/replay`, and `GET /webhooks/{id}/events/{event_id}/attempts` actually work as documented (they're absent from `openapi.json` entirely, so this skill currently trusts only the docs' own curl examples, which is thinner evidence than usual).
20. **Gmail complaint-reporting gap.** Hard to verify without a real Gmail recipient marking a real email as spam — lower priority / opportunistic only if a real scenario arises naturally.

## Priority 6 — lower priority / rounding out the reference files

21. **Attachment size boundary.** Send an email just under and just over 40MB (post-Base64) and confirm the exact failure mode at the boundary (which error type, whether it's caught before or after upload).
22. **Blocked attachment extensions.** Attempt to send a `.exe` or `.js` file as an attachment and confirm the actual failure mode — `references/sending-emails.md` currently flags this as `⚠ 文档未说明`.
23. **`template` + `html` mutual exclusivity — exact error.** Send a request with both `template.id` and `html` set, confirm the exact validation error type/message (currently only "presumably" a validation error per the API reference prose, message not quoted).
24. **Template variable enforcement.** Publish a template with a required variable, send without providing it, confirm the exact validation error (`references/templates-and-react-email.md` currently just says "a validation error", untested).
25. **Scheduled-email cancel-then-reschedule.** Confirm cancel really is terminal (attempting to reschedule a canceled email fails) as the docs' `<Warning>` claims.
