# 幂等与重试：Idempotency-Key

> ⚠ 本文件全部内容转录自 docs.stripe.com（抓取于 2026-09-21），未经真实 API 调用验证。

## 为什么支付类 API 特别需要这个（而通用 REST API 直觉里容易漏掉）

普通 Web API 调用超时，很多人的直觉反应是"再发一次请求"。**对支付类 API，这个直觉是危险的**：网络超时意味着你不知道 Stripe 到底有没有处理这次请求——请求可能根本没到达 Stripe，也可能 Stripe 已经处理完、只是响应没送回来。如果这是一次"创建 PaymentIntent 并 `confirm=true`"或者"创建 Refund"的请求，裸重试有真实的**双重扣款/双重退款**风险。这正是 `Idempotency-Key` 存在的原因,也是这个机制在通用后端开发经验里不常见、但在支付 API 场景下必须掌握的一条规则。

## 精确机制

在请求 header 里加：

```
Idempotency-Key: <一个足够唯一的字符串,最长 255 字符>
```

**行为**（⚠ 文档原文）：
- Stripe 会缓存**第一次**用某个 key 发起的请求所对应的状态码和响应体（不管这次请求成功还是失败,包括 5xx）。
- 之后用**同一个 key**重试,只要请求的 endpoint 和参数跟第一次完全一致,Stripe 直接返回缓存的结果,**不会再执行一次实际操作**。响应里会带 `Idempotent-Replayed: true` 表示这是被重放的缓存结果。
- key 从系统里自动清除的时间是**至少 24 小时**之后；超过这个窗口后同一个 key 会被当成全新请求处理。
- 如果同一个 key 配的参数和第一次不一致,返回 `idempotency_error`(防止误用同一个 key 表示了两个不同的操作)。

**适用范围**：所有 `POST` 请求都接受幂等键。`GET`/`DELETE` 请求本身天然幂等(重复调用不会产生副作用),**不需要也不应该带这个 header**。

## key 生成策略

两种常见做法(⚠ 文档原文推荐)：
1. **随机字符串,足够的熵避免碰撞** —— UUID v4 是官方举的典型例子。
2. **从你自己业务对象的 ID 派生** —— 比如用购物车 ID、订单号作为 key(或加上一个操作类型前缀拼出 key)。这种做法额外带来"天然防重复提交"的好处：同一个购物车不小心被提交两次,幂等层直接帮你挡掉。

**不要用敏感数据**(邮箱、身份信息等)做 key 的原始材料(⚠ 文档原文提示)。

## 各类失败场景怎么重试

| 场景 | 该怎么做 |
|---|---|
| **网络错误 / 超时**(没收到任何响应) | 用**同一个** idempotency key 重试,安全,这正是这个机制设计要覆盖的核心场景 |
| **`4xx`(如 400 参数错误)** | ⚠ 陷阱：直接用同一个 key 重试只会拿到缓存的同一个 400,**不会**重新校验。要先修正参数,**再生成一个新的 idempotency key** 发起请求。少数 4xx(429 限流、401 缺失 API key)是在幂等层之前就被拦截的,不受这条限制,但官方建议"最安全的策略是所有 4xx 都换新 key" |
| **`5xx`(Stripe 服务端错误)** | 可以用同一个 key 重试,通常会拿到相同结果(因为幂等层已经缓存了执行结果)。但官方文档说明 500 的实际业务状态属于"不确定"(indeterminate)——Stripe 内部会尝试对账修复,可能事后补发 webhook 通知实际发生了什么。**遇到 500 时,除了在网络层重试,也建议配合监听 webhook 来最终确认这次操作到底有没有生效**,不要只凭一次 500 响应就断定"肯定没成功" |
| **限流 `429`** | 幂等层在限流检查**之后**才生效,同一个 key 重试可能拿到不同结果(第一次被限流拒绝、第二次真的执行了)。指数退避后重试,具体见 [errors-and-limits.md](errors-and-limits.md) |

## SDK 自动重试

官方 SDK 大多提供"自动重试 + 自动生成幂等键"的配置项(需要显式开启,不是默认行为;⚠ 文档原文举了 Ruby 的例子 `Stripe.max_network_retries = 2`,其他语言的具体配置项名称请查对应 SDK 文档,未逐一核实)。开启自动重试后,SDK 会在第一次失败后很快重试一次,之后按指数退避安排后续重试——这个机制假设单次失败多是偶发的,连续失败才代表真正的系统性问题。

如果手写重试逻辑(没用 SDK 的自动重试),响应里的 `Stripe-Should-Retry` header 可以作为判断依据:
- `true`:可以重试(仍然建议配合退避等待,不要立刻重试)
- `false`:不要重试,重试也不会有不同结果
- 未出现该 header:无法从这个信号判断,退回看 HTTP 状态码自行决定

## 幂等键 vs 业务层去重

幂等键解决的是"同一次操作的网络层重试不产生副作用",**不是**用来防止"用户不小心点了两次提交按钮发起了两个本意不同但参数恰好一样的请求"这种业务语义上的重复——如果 key 是纯随机生成的(比如每次请求都新生成一个 UUID),幂等机制完全不会挡住这种情况。**如果幂等键是从业务对象 ID 派生的(策略 2),则天然具备一部分防重复提交的效果**,这也是官方推荐这种做法的原因之一。要不要用幂等键做业务层去重,取决于生成 key 的策略,不能假设"传了 Idempotency-Key 就自动防住了所有形式的重复"。
