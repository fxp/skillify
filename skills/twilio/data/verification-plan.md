# Twilio skill — verification plan

Status: this skill (`../twilio/`) was produced from steps 1–2 of the `create-doc-skill` methodology only (fetch real docs + OpenAPI specs, structure them into SKILL.md + references/). Step 3 (real API verification) and step 4 (with/without comparison) were **not done** — no Twilio credentials were available at authoring time (2026-09-21). This file is the priority-ordered list of what to test once credentials are available, per `create-doc-skill/references/verify.md`'s "没有 key、或 key 权限不够时" fallback plan.

Cost/risk profile note: unlike a pure compute API, Twilio actions have small but real per-use costs (SMS segments, voice minutes) and a fresh trial account starts with free product-specific units (100 SMS, 75 voice minutes per the trial docs) plus a hard restriction to ~5 "Verified" recipient numbers and the sign-up country. **Do all verification below against a trial account's own verified test number first** — this keeps Priority 1–2 essentially free and avoids needing a paid account just to confirm the basics. Only Priority 4 (international pricing/E.164 destinations, load-bearing production checks) may need an upgraded (payment-method-attached) account.

## Priority 1 — cheap, structural, "does the auth model and the 30-second example even work"

These gate everything else; if wrong, most of the skill is wrong.

1. **Confirm Basic Auth, both credential pairs.** Run the SKILL.md "30-second first run" curl and Python example exactly as written, once with Account SID + Auth Token, once with an API Key SID + Secret (Main key). Confirm both succeed identically. Then deliberately send `Authorization: Bearer $TWILIO_AUTH_TOKEN` instead of Basic Auth and capture the **exact** HTTP status + error body — confirm/correct the claim in `references/auth.md` that this produces 401 / error code 20003 specifically (vs. some other 401 variant, e.g. a generic unauthenticated response with no Twilio error code at all). **Expected cost: 1 SMS segment (~$0.0079 US) plus failed auth attempts, which are free.**
2. **Confirm a Standard API key is rejected on `/Accounts` and `/Keys`.** Create a Standard-type key, attempt `GET /2010-04-01/Accounts.json` and `GET /v1/Keys` with it, confirm the documented "requires Main key" restriction and capture the exact error (still 20003? different message?). **Expected cost: free (read-only, no message/call sent).**
3. **Confirm the E.164 rejection is synchronous, not silent.** Send a Message create request with `To` malformed (e.g. `(415) 555-2671`, no `+`). Confirm: HTTP status, whether it's exactly error 21211, and the exact `message` string returned — this is the single most load-bearing unconfirmed claim in `references/send-sms.md` and directly backs eval scenario 2. Repeat once for `From` malformed/not-owned (expect 21401) and once for Verify's `To` (expect 60200) to confirm the three domains really do use different codes for "the same kind of mistake." **Expected cost: request should reject before any segment is billed — confirm this is actually true (i.e. that a 400 response really means $0 charged, not charged-then-refunded).**

## Priority 2 — the "intuition trap" claims that drive SKILL.md's cross-cutting rules

Each corresponds to one `evals/evals.json` scenario.

4. **Verify two-step flow, end to end (eval scenario 3).** Create a Verify Service, `POST .../Verifications` with `Channel=sms` to your own verified trial number, confirm the response has no code and `status: "pending"`. Read the actual SMS, then `POST .../VerificationCheck` with the real code and confirm `status: "approved"`. Then repeat with a deliberately wrong code and capture: HTTP status (is it still 200/201?), the `status` field value on a wrong-code response (does it become `"pending"` still, or something else on the very first wrong attempt?), and confirm the doc claim that a wrong code is not itself an HTTP error. Then exceed the max-check-attempts a few times and confirm error 60202 fires with the documented shape. **Expected cost: ~1 SMS segment for the OTP send.**
5. **TwiML vs JSON on an inbound webhook (eval scenario 4).** Point a Twilio phone number's "A message comes in" webhook at a small test server. Text the number, capture the exact inbound request (confirm it's `application/x-www-form-urlencoded`, list the actual parameter names received — the docs warn these can change/expand without notice, so a live capture is the only reliable source). Have the server respond with valid TwiML `<Message>` reply and confirm the reply SMS arrives. Then deliberately have it respond with a JSON body instead and confirm what actually happens — does Twilio surface an error code (12300 per the docs) visibly anywhere (Console debugger, a status callback), and does the original inbound message still register as "received" on your side? **Expected cost: 2 SMS segments (in + reply).**
6. **Signature validation, both content types.** Using the SDK's `RequestValidator`, validate a real captured inbound webhook request's `X-Twilio-Signature` against the Auth Token, confirm it validates. Deliberately validate with the API Key secret instead of the Auth Token and confirm it fails (backs the "these are not interchangeable" claim in `references/webhooks-and-signatures.md`). If feasible, also capture one JSON-body webhook (a newer event type, if the account has one configured) and confirm the `bodySHA256` + `validateRequestWithBody` flow. **Expected cost: free (validation is local, no Twilio call).**
7. **`<Gather>` default-action looping behavior (voice).** Build the minimal `<Gather>`-with-no-`action` TwiML example from `references/voice-calls-and-twiml.md`, call it from a trial-verified test number, enter digits, and confirm it really does loop back to the same document (vs. Twilio having changed this default at some point). **Expected cost: a few voice minutes on trial free units.**

## Priority 3 — pricing and error-code table accuracy

8. **Pricing API shape and a real cross-country comparison (eval scenario 5).** Call `GET /v1/Messaging/Countries/US`, `/IN`, `/GB` with real credentials, confirm the response shape matches what's documented in `references/pricing-and-errors.md` (array of per-carrier records, not a single price), and record the actual current per-segment prices for these three countries side by side to put a real number behind "varies wildly" (currently just asserted, not quantified) — this makes the eval scenario's expected answer concrete instead of qualitative.
9. **Confirm `price`/`error_code` async-population timing.** Send a real Message, immediately read the create response (confirm `price: null`), then poll the resource a few seconds later and confirm `price` populates once status reaches a terminal state. Repeat by deliberately sending to an invalid-but-E.164-formatted number that will fail at the carrier (if a safe way to trigger this exists on a trial account) to see a real 30xxx-range `error_code` on the async resource, distinct from the create-time 21xxx-range rejection.
10. **Trial-mode-specific error (14111).** Attempt to send to a syntactically valid E.164 number that is NOT one of the account's ~5 verified trial numbers, confirm error 14111 fires (not 21211/21401), and capture its exact message — this is the concrete evidence behind SKILL.md rule 8 ("check trial status before debugging E.164 formatting").

## Priority 4 — voice call creation and TwiML edge cases (lower priority / needs a live call)

11. **Outbound call `Url` vs `Twiml` parameter.** Create a call with `Url` pointing at a TwiML-serving endpoint, confirm Twilio fetches it and executes the returned TwiML. Separately create a call with the inline `Twiml` parameter (no `Url`) and confirm the "absolute action URLs required" caveat for nested `<Gather>`/`<Record>`/`<Pay>` actually manifests (a relative action URL should behave differently or error).
12. **Answering Machine Detection + `SendDigits` mutual exclusion.** Confirm the documented claim that providing `SendDigits` causes `MachineDetection` to be silently ignored (a silent-failure-shaped interaction worth confirming precisely, per `create-doc-skill/references/verify.md`'s guidance that silent failures are the most dangerous class of doc-vs-reality gap).
13. **DialCallStatus values in practice.** Trigger a few real `<Dial>` outcomes (answered, busy/no-answer if testable, an intentionally invalid number for `failed`) and confirm the `action` callback's `DialCallStatus` values match the documented enum exactly.
