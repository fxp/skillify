# 真实凭证到位后的验证计划

按优先级排列；每项写明要测的结论、用哪个 endpoint、预期成本、怎么判定。全部为只读或低成本操作，除非特别标注。

## P0（鉴权链路，阻塞其他所有验证）

1. **`GET /cgi-bin/token` 与 `POST /cgi-bin/stable_token` 用真实 appid/secret 各换一次 token**，确认响应结构与 `references/auth.md` 一致；用同一对 appid/secret 分别换，确认两个接口返回的 `access_token` 字符串确实不同（验证"互相隔离"的说法）。成本：0，判定：两次响应的 `access_token` 值不相等即可证实隔离。
2. **用 `stable_token` 的 `force_refresh=true` 验证旧 token 失效**：先用 `force_refresh=false` 换一次拿到 token A，再 `force_refresh=true` 换一次拿到 token B，然后用 token A 调一个只读接口（如 `cgi-bin/tags/get`），确认是否报 `40001`/`42001`。判定文档"会导致上次的 access_token 失效"是否准确。

## P1（本 skill 标了 ⚠ 但未证实的地方，逐条对应 reference 位置）

3. **`events.md` 数据格式矛盾**：在账号后台把"数据格式"配置为 XML 和 JSON 各测一次，用 debug 工具（`apiExplorer?type=messagePush`）触发 `debug_demo` 事件，确认回调收到的包体格式是否真的可选，还是实际只支持 XML。
4. **`events.md` AES 的 IV 推导**：用官方 debug 工具生成的测试向量（请求构造 + 调试工具两个入口）离线验证 IV 是否等于 `AESKey` 前 16 字节；不确认就不要在 SKILL.md 里断言这一点。
5. **`messaging.md` 客服消息超额行为**：48 小时/5 条 或 1 分钟/3 条配额用完后再调用 `message/custom/send`，记录返回的 `errcode`/`errmsg`。成本：需要真实测试用户与公众号互动，无法在无凭证阶段完成。
6. **`template-subscribe.md` 三套机制的账号开放状态**：登录测试账号后台"添加功能插件"页，确认当前账号实际开放的是模板消息、订阅通知，还是两者都开放；如果两者都开放，各发一条真实通知，对比 `data` 键名格式（`.DATA` 后缀 vs 裸键名）哪个能真正下发成功。
7. **`users.md` 批量取消标签的条数上限**：`batchtagging` 文档写明 50 个，`batchuntagging` 未写明；用 51 个 openid 测试 `batchuntagging` 是否报错，确认是否同样限 50。
8. **`menu.md` 字数限制**：创建一个刚好 5 个汉字的一级菜单名（超出"4 个汉字"但未超"16 字节"的临界值），确认创建是否成功、客户端实际显示是否被截断，判定字节数口径与汉字数口径哪个是真实生效的限制。
9. **`menu.md` 个性化菜单优先级**：创建两条匹配规则有重叠的个性化菜单（如都匹配同一个 `tag_id`），用 `trymatch` 测试落在重叠范围内的用户命中哪一条，确认优先级规则。
10. **`errors-and-limits.md` `40001` 与 `40014` 的区别**：分别构造"access_token 格式错误"和"access_token 过期"两种场景（后者需要等 7200 秒或用已知失效的 token），对比两个错误码各自的触发条件。

## P2（需要额外资源/权限，暂不计划做）

11. **`events.md` 服务器配置与接入校验实测**：需要一个公网可访问的服务器接收微信的 GET 校验请求，超出本机测试范围，暂不安排；有公网环境后按 `references/events.md` 第 2 节的签名算法实现并用官方 debug 工具触发验证。
12. **模板消息/订阅通知的真实送达确认**：需要真实关注用户 openid，且模板消息/订阅通知每次发送都是有副作用的操作（会真的推送给用户），只在测试账号 + 测试用户环境下按需做，不在批量验证阶段进行。
13. **官方加解密示例代码校对**（`cryptoDemo.zip`）：按 BRIEF 规则不下载安装任何压缩包/SDK 资料包，只能在浏览器里查看到该资源存在；若需要逐行核对 PKCS7/IV 实现，需要人工下载后在隔离环境里对照，不在本 skill 的自动化验证范围内。

## 判定标准

- 每项验证完成后，把结论按 `verify.md` 规定的格式写回对应 `references/*.md`："**已用真实 API 验证（日期）**：... 返回 `...`"，并同步更新 `SKILL.md` 的「⚠ 验证状态」一节。
- 发现与当前 skill 描述不一致的地方，用 `<!-- Gap: ... -->` 标注并升级到 SKILL.md 的"文档自相矛盾"汇总。
- 涉及真实用户/真实消息的验证（5、6、12），完成后清理测试产生的标签、黑名单条目、自定义菜单等，不在测试账号里留垃圾配置。
