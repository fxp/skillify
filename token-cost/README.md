# Token 成本分析（GLM-5.3 基准，182 次运行）

## 结论先说

**"用了说明书之后总 token 消耗下降"这个说法，数据不支持。**

按每次运行算，读说明书的一侧**更贵**：线上总 token **+30.2%**（Mann-Whitney p = 0.0001，显著）。
cache 把这个差距吸收掉了大部分，折算后只剩 **+6.9%**（p = 0.15，不显著）——
但方向仍然是更贵，不是更省。

真正下降的是**每完成一次正确任务的成本**，而且这个优势有很强的前提，见下。

## 数据来源与两个必须处理的坑

数据来自 Claude Code 自己的会话记录 `~/.claude/projects/<cwd-slug>/*.jsonl`，
每条 assistant 消息都带 `usage`，含 `cache_creation_input_tokens` / `cache_read_input_tokens`。
182 次运行**全部**找到了 transcript，没有缺失。

两个坑都会把结论做假，都已修正：

1. **Claude Code 的 JSONL 每个 content block 写一行，每行都带完整 usage。**
   同一次 API 调用会出现好几行——实测一次运行 52 条带 usage 的记录，
   按 `message.id` 去重后只有 **13 次**真实调用。不去重的话 token 数虚高约 4 倍。
2. **有 6 次运行因 900 秒超时被重跑过，目录下有两份 transcript。**
   主口径只取产出交付脚本的那一次；把所有尝试都算进去的口径用 `--all-attempts`。
   这 6 次里 **5 次在 baseline 侧**——没有说明书就得花更多时间查文档。

> 我第一版没处理这两点，跑出来是"skill 省 40%"。那个数字是假的。

## 一、每次运行的成本

| 指标 | skill | baseline | 差 | Mann-Whitney p |
| :--- | ---: | ---: | ---: | ---: |
| 线上总 token | 456,917 | 350,844 | **+30.2%** | **0.0001** ✅ |
| 线上总 token（中位数） | 388,476 | 278,362 | +39.6% | |
| 计费当量（cache 折算后） | 137,779 | 128,906 | **+6.9%** | 0.15 |
| 计费当量（中位数） | 133,058 | 112,515 | +18.3% | |
| **WebFetch 次数** | **2.4** | **6.6** | **−63.9%** | **0.0000** ✅ |
| 对话轮数 | 9.7 | 9.8 | −0.6% | 0.18 |
| 工具调用次数 | 10.3 | 11.7 | −12.3% | |

数据右偏（少数运行极贵），所以用 Mann-Whitney U 而不是 t 检验。

**唯一稳健且显著的行为差异是 WebFetch 少了 64%**——说明书确实替代了"上网查文档"这件事，
但省下的抓取成本，抵不过把说明书本身读进上下文的成本。

## 二、cache 起了多大作用

| | 输入侧合计 | 其中 cache 命中 | 未命中 | cache 写入 | 输出 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| 读了说明书 | 446,242 | 402,040（**90.1%**） | 44,203 | 0 | 10,675 |
| baseline | 337,147 | 307,473（**91.2%**） | 29,674 | 0 | 13,697 |

**两侧的 cache 命中率几乎一样（90% vs 91%）**——说明书并没有让 cache 更好用或更差用，
它只是把输入侧整体推高了。

cache 的作用体现在**折算**上：

```
不计 cache 折扣（按线上 token 直接比）： skill +30.2%
计入 cache 折扣（cache 读只算 0.1 倍）：  skill  +6.9%
```

**cache 把说明书的额外成本吸收掉了约四分之三。** 这是"考虑 cache"这件事最实际的意义：
说明书那几万 token 只在第一次进上下文时是全价，之后每一轮都按十分之一计。

> ⚠️ **一个对 skill 有利的偏差，必须写在明面上**：这个端点**从不报告 `cache_creation_input_tokens`**
> （182 次运行全是 0），但 `cache_read` 很大。也就是说折算里给了 cache 读 0.1 倍的便宜，
> 却从来没有付过 1.25 倍的写入代价。所以 **+6.9% 是对 skill 最有利的算法，+30.2% 才是与供应商无关的硬数字。**
> 权重用的是 Anthropic 的官方比价（cache 写 1.25×、cache 读 0.1×、output 5×）；
> 智谱 Coding Plan 是配额制不按 token 计价，所以这里给的是"当量"而非金额，换任何一家的价格都可以重新加权。

## 三、每完成一次「正确」任务的成本

只有满分才算成功。总花费 ÷ 成功次数：

| 口径 | skill | baseline | 差 |
| :--- | ---: | ---: | ---: |
| 全部 19 个场景（计费当量） | 151,059 | 213,281 | **−29%** |
| 全部 19 个场景（纯 wire，不给 cache 折扣） | 500,957 | 580,488 | −14% |
| **剔除 baseline 0/5 的 5 个场景** | 148,313 | 157,243 | **−6%** |
| **场景级比值中位数**（每场景一票，同样剔除） | — | — | **+4%** |

成功次数：skill **83/91**，baseline **55/91**。

**这里必须诚实**：−29% 这个数字几乎全部来自 **5 个 baseline 一次都没成功的场景**
（`batch-best-model`、`pdf-reuse-fileid`、`cited-web-answer`、`get-params-style` 等）——
baseline 在那些场景里每次成功的成本是无穷大，把平均值拉垮了。

把那 5 个场景剔掉之后，优势只剩 **−6%**；再按"每个场景一票"取中位数，
结果是 **+4%**，也就是**典型场景下 skill 每次成功反而略贵**，14 个场景里只有 6 个更省。

## 四、按平台

| 平台 | 每次运行 wire | 每次运行计费当量 | 每次成功计费当量 |
| :--- | ---: | ---: | ---: |
| bigmodel-cn | +46.7% | +11.9% | 139,990 vs 193,006（**−27%**） |
| autodl | **−24.1%** | **−19.8%** | 107,920 vs 201,795（**−47%**） |
| volcengine-ark | +27.6% | +13.6% | 239,977 vs 295,728（−19%） |

**AutoDL 是唯一一个连每次运行都更省的平台**（wire −24%）。原因很具体：
它那个显著场景（`get-params-style`）的官方文档把传参方式写错了，
baseline 会反复抓文档、反复试错；有说明书就是一次写对。这正是"说明书替代查文档"最理想的形态。

## 怎么复现

```bash
cd token-cost
python3 aggregate_tokens.py --json tokens.json   # 采集原始 usage
python3 analyze.py --json                        # 统计与检验
python3 analyze.py --all-attempts                # 把超时重跑的尝试也算进成本
```

## 边界

- 只测了一个执行器（GLM-5.3）和一个 harness（Claude Code CLI）。换 Agent、换上下文管理策略，数字会变。
- 计费当量的权重是 Anthropic 比价；该端点不报 cache 写入，折算对 skill 有利（见上）。
- "成功"的定义沿用各轮冻结的判分标准，满分才算。判分标准变了，每次成功的成本也会变。
- 说明书本身的大小直接决定额外成本：`bigmodel-cn` 有 10 份 references，是三者里最大的，
  也正是每次运行 wire 涨得最多的那个（+46.7%）。**精简说明书可以直接改善这个数字。**
